# Blygger — Project Instructions

> Environment rules, keys & safety policies: see [`Code/CLAUDE.md`](../CLAUDE.md), `warnings.md`, `warnings-node.md`, `warnings-keys.md`, `security-policy.md` at the `Code/` level.

Blygger is an AI-native decentralized public writing medium — fragments + threads + TK-transclusion over static files + RSS. Public repo: `blygger/blygger-spec` (branch `main`), part of the `blygger` GitHub org alongside the `blygger-org` and `blygger-com` site repos (session 6 rename + scaffolding — see `../CLAUDE.md`). This folder is the **protocol** project — normative text, plan docs, and the program's devlog. The reference client moved out at session 26 (2026-09-28) and is now [`blygger/blygger-studio`](https://github.com/blygger/blygger-studio), checked out at [`../blygger-studio/`](../blygger-studio/); `worker/` no longer exists here. Venkat's *personal blyg deployment* will live separately in `Publishing/`.

**Four repos, four tracks.** The program roadmap is [`docs/roadmap-tracks.md`](docs/roadmap-tracks.md) — core protocol (here), reference client (`blygger-studio`), registry/discovery (`blygger-com`), developer community (`blygger-org`). This repo keeps the session ritual and the single `DEVLOG.md` for all four.

## Locked decisions (do not relitigate without Venkat)

1. **Protocol = static file contract** under the blyg origin (mounted anywhere per decision #14; reference default `/blyg/`): `items/{id}.json` is the state plane (ground truth, full archive); `feed.xml` is the notification plane (lossy RSS, just a signal).
2. **IDs**: stable random 128-bit IDs for identity; per-version content hashes for integrity/IPFS. Never content-addressed IDs.
3. **Studio/page split**: every client = private studio (dynamic, unconstrained) + public page (the `/blyg` artifact, protocol-governed). The protocol governs *only* the page.
4. **Conformance levels** L0–L3, strict supersets; clients ignore unknown constructs; every blyg feed stays a valid RSS feed with self-contained HTML per item.
5. **AI is never in the protocol.** Generation is studio-side at authoring time; the page publishes output + provenance.
6. **Roadmap order** (restructured session 3, with Venkat; **amended session 12, 2026-08-10, Fable + Venkat**): no-AI core first; both core abstractions in the first release. Build order after the session-12 amendment: v0.1 publish → v0.2 subscribe → **TK-core (pulled forward from v0.4** — depends only on v0.1; matches the session-11 release bar of TK + pubsub**)** → v0.3 threads-cross-client → v0.4-remainder (filter plugins, staleness-over-DAG, auto-hoppers) → v0.5 RAG/polish → v1.0 freeze.
7. Private content in v1 = never-published drafts (owner-only). Privileged-group access is deferred to L3.
8. **Withdraw + pin model** (session 3, supersedes tombstone/silent-unpublish): no permanent delete of published items — the single exit is *withdraw*, a permanent reversible endcap (`kind: "withdrawn"`, 200 forever, one feed entry, compliant clients roll up to null); *pins* are irrevocable per-version hosting promises (`items/{id}/v{n}.json`) that survive withdrawal; only pinned versions are exposed, pinning never forces a fork; `forked_from` is reserved for v0.3. Rationale: `docs/proposals/retract-pin-fork-proposal.md`.
9. **Transclusion grammar** (session 3): `![[id]]` on its own line, `![[id@vN]]` reserved; publish-time snapshot baked into self-contained HTML with `{id, version}` provenance; fragments-only nesting in v0.1; **no auto-pin** — pins remain a separate deliberate act; source withdrawal never cascades into thread snapshots. Spec: `docs/v0.1-plan.md` §2.9.
10. Licensing: MIT (code), CC-BY-4.0 (`docs/`).
11. **Author/identity model** (session 5): `author` is an optional, per-item, origin-scoped, client-asserted, *opaque* pass-through object (`name` recommended, `url` optional, all other members = the client's private authorspace grammar) — no protocol guarantees or representations about it; authors are never addressable; the only protocol-authenticated entity is the client/origin. **Identity, like AI, is never in the protocol.** Feed invariant narrowed from single-*author* to single-**publisher**: multiplayer clients may publish one conformant feed with per-item bylines (no shared namespace, no `user@server`, DNS remains the namespace). Decision record: `docs/proposals/author-field-proposal.md`.
12. **Response primitives & curation** (session 7): no reply primitive, ever (frozen-spec stance, reaffirmed); transclusion is the primitive, stub is the gesture; **make-public for imported items = curation display only** (public hopper page, local snapshot, source attribution) — imported items are **never re-emitted on the publisher's feed** (would collide with `blyg:id` rollup + single-publisher invariant); feed-speech about others' content costs editorial (stub or fork-from-pin). No tags, no canned phrases in protocol — hoppers are the taxonomy, stub templates are studio sugar. Third leg of the pattern: **editorial convenience, like AI and identity, is never in the protocol.** Decision record: `docs/proposals/curation-discovery-generation-proposal.md`.
13. **Discovery model** (session 7): two planes, both **L2 and optional** — static plane = curated OPML blogroll (origin-relative `blogroll.opml` + manifest key, ships v0.2; no completeness claim); notification plane = **Webmention** (W3C, reused not invented) with **structural verification** (receiver checks the source item JSON actually names the target), ships v0.3; verified mentions are studio signals feeding detect-stubs, never auto-published. "Follow" is deliberately nothing: subscription stays client-local and invisible; no follower lists/requests/objects ever — the public graph is blogrolls (outbound) + verified stubs (inbound). The Webmention receiver is the protocol's first dynamic surface, acknowledged as an amendment carve-out to decision #1: optional-at-L2, "just files" stays the L1 floor. ActivityPub/WebSub/directories rejected (records in the proposal doc).
14. **Mount independence** (session 8, Fable + Venkat): a blyg's origin is *any* absolute base URL — domain root, any path, any subdomain; the surface is strictly origin-relative and no protocol construct may assume a path component (readers MUST NOT infer anything from the mount). **Wire vocabulary and deployment lexicon are formally split:** manifest filename `blyg.json`, `"blyg"` version key, `blyg:` GUID/XML elements are protocol-permanent; the *mount* is per-deployment config (`Env.MOUNT`, reference default **`/blyg`**, `""` = root). The path is the deployer's, the filename is the protocol's; the fixed filename is the discovery anchor that keeps free mounts findable. (Token spellings in this record amended by #16 — originally `blygg.json`/`blygg:`.) Consequence: v0.2 autodiscovery may not probe a fixed path — treat-URL-as-origin + `<link rel="blyg">` + conventional-mount fallback, mechanics finalized in the v0.2 plan (⚠️ FABLE). Supersedes task 16's slug-drives-path conflation; spec §4, plan task 17.
15. **Spec publishing model** (session 8, Fable + Venkat): the normative spec is published at semantic versioned URLs — `blygger.org/spec/{version}/` (latest; "freezes at stable" amended by #21: pre-1.0 versions never freeze, only 1.0 does) + `/spec/{version}/{date}/` immutable snapshots + `/spec/` index — with each snapshot paired to a `spec/{version}/{date}` git tag in `blygger-spec` and every published page footer-stamped with its source commit. **The spec is never published as a blyg**: spec URLs must be semantic/citable vs. deliberately opaque item ids; a normative document is the wrong shape for fragment/thread primitives; the normative text must not depend on the machinery it defines. Deferred, not rejected: an announcements blyg (v0.2+) and a ceremonial 1.0 pin. Reference-impl releases (`ref-v*` tags) are loosely coupled — site links to stable Releases URLs, no lockstep deploys. Plan: `docs/spec-publishing-plan.md`. (Doc lifecycle across protocol versions formalized by #23.)
16. **Vocabulary rule: blyg/blygger, `blygg` retired** (session 9, 2026-08-05, Fable + Venkat): the noun is **blyg** (one g — as *blog* is to *blogger*) and the protocol/brand name is **blygger** (the `ygg` gesturing at Yggdrasil); the intermediate spelling `blygg` is retired everywhere, including the wire. Amends #14's token spellings without touching its architecture — the wire/mount split stands, but the wire tokens are now `blyg.json` (manifest filename), `"blyg"` (JSON version key), `blyg:` (XML ns prefix, GUID scheme `blyg:{id}:v{n}`), `blyg-transclusion` (baked blockquote class), `<link rel="blyg">` (reserved autodiscovery); mount default stays `/blyg`, so path and filename now happen to agree — a convention coincidence, not a protocol linkage (#14's origin-relativity rules unchanged). Cost was zero because nothing is deployed (task 11's D1 id is still the placeholder); after first deploy this would have been a breaking wire migration. Spec is DRAFT so no version bump; recorded here and in DEVLOG per the spec's own change rule. Historical records (`DEVLOG.md`, `RENAME.md`, `ygg-initial-spec.md`) deliberately keep the old spelling.
17. **Resolution algorithm & subscription identity** (session 12, 2026-08-10, Fable): given any URL, resolution is deterministic, ordered, and bounded (≤ 6 fetches): normalize → direct `blyg.json` probe → feed-upgrade via `<blyg:manifest>` → one-hop `<link rel="blyg" href="{origin}">` → conventional-mount probes (`/blyg/`, root) → RSS fallback (L0). **Subscription identity = final fetch origin** (post-redirect), never the manifest's self-asserted `site` — a mirror must not inherit another origin's identity; disagreement is surfaced, not adopted. Adopting a new origin on re-resolution is always user-confirmed. Blogroll is **standard OPML 2.0 with no extensions** — the `blyg:manifest` feed element makes plain OPML blyg-resolvable, so nothing custom is needed. Mechanics: `docs/v0.2-plan.md` §2.
18. **Importer invariants** (session 12, 2026-08-10, Fable): (a) **the archive index is the reconciliation surface; the feed is a cheap trigger** — gaps, skew, and malformed feeds degrade to an index diff, never to loss; (b) **the item document is ground truth for content, but the local version watermark never silently regresses** — a lower-than-watermark version is surfaced as a suspected history rewrite, reset only by the user; (c) **retention past withdrawal follows the origin's own serving surface** — readers may retain exactly what the origin still serves (pinned versions) and MUST roll everything else to null, which settles hopper-copy-vs-withdrawal; (d) version keys are informative (`"0.x"` accepted with ignore rules, publishers emit what they implement). State machine: `docs/v0.2-plan.md` §3.
19. **Versioning stays a bare counter; pins are the significance primitive** (session 12, 2026-08-10, Fable + Venkat): `version` remains a bare positive integer, +1 per publish event — no semver, no edition field, no significance markup on the wire, at any level. Semver rejected (breaks the load-bearing +1 discipline behind #18's watermark, restructures wire-permanent tokens post-deploy, encodes API-compatibility semantics prose doesn't have); an additive author-asserted `edition` field also rejected, on design-intent grounds: **an edition bump is cheap talk; a pin is a costly signal** — the protocol's machine-readable "this state matters" is the pin (§8), backed by an irrevocable hosting promise, and publishers should think consciously in pins rather than in version-structure skeuomorphism. Auto-pin heuristics dissolve into pin-suggestion studio UX (fourth application of the standing pattern: significance markup, like AI/identity/editorial convenience, is never in the protocol). Decision record: `docs/notes/tn-1-versioning-and-pins.md` (the first technical note — genre + publishing pipeline defined in `docs/spec-publishing-plan.md` §5).
20. **TK authoring contract** (session 12, 2026-08-10, Fable): instructed generation is a **two-layer split** — the TK grammar (`[TK]instruction[=]output[/TK]` since the session-16 respelling below, inline or block, no nesting, valid in fragment and thread working copies) is **studio-private pre-generation state that never reaches the wire**; published `content_md` is ordinary marker-free markdown (the hash covers exactly what readers read), with provenance as an optional item-doc `"generated"` array (`{sources:[{id,version}], model, at}` per scope; no instruction bytes ever) plus a baked `blyg-tk-gen` HTML class — mirroring transclusion's two-plane pattern, and amending the §4 item-3 inert-markers lean. **Quote-vs-source rule** (resolves §4 item 6 without touching #9): outside TK scopes, own-line `![[id]]` is a transclusion (verbatim quote, `transclusions[]`), unchanged; **inside a TK scope every `![[id]]` is a source reference** — content fed to the generator, disclosed in `generated[].sources`, never a blockquote; scopes cannot contain transclusions (compose by exclusion). Generation is always an explicit, author-reviewed studio act — publish with unresolved scopes is an error, publish never triggers generation. Disclosure is SHOULD-record in spec language, always-recorded in the reference client (self-asserted like all provenance). One provider-call interface serves every present and future hook. Plan + rationale: `docs/tk-core-plan.md`. **§2.1 grammar confirmed (session 15, 2026-09-11, Fable):** no `]` terminates the instruction; any closing token beginning with `]` mis-splits an instruction ending in a `![[id]]` source ref — the primary case instructions exist to carry. That constraint is forced and stands. **§2.1 grammar respelled to balanced tokens (session 16, 2026-09-11, Fable + Venkat):** the scanner tokens are now `[TK]`, `[=]`, `[/TK]` — typed forms `[TK]instruction[/TK]` (ungenerated) and `[TK]instruction[=]output[/TK]` (generated). Venkat rejected the session-12 unbalanced opener (`[TK` with no closing bracket) as unreadable; the session-15 argument only rules out `]`-*initial instruction terminators*, and the opener's `]` sits before any instruction text, so the balanced spelling was always compatible — it is also what the frozen v0 spec, roadmap, and session-11 proposal examples all wrote informally. Readability is now an explicit grammar objective. No wire impact (grammar is studio-private); old-spelling working copies on the two test nodes are migrated or discarded, not dual-supported (pre-release, per #21). Implementation task list: `tk-core-plan.md` §9 (Sonnet/Opus-safe).
21. **Development-phase strategy: pre-1.0 spec is always draft; 1.0 is the release event** (session 12, 2026-08-10, Venkat): building the reference implementation **is** testing the protocol — the spec changes in response to testing discoveries at any version < 1.0, and **no pre-1.0 spec version is ever declared stable** (supersedes the freeze-0.1-at-stable intent). v1.0 is the first version we stand behind, published to a larger audience at a deliberate release event; until then spec users and implementation builders should assume **no promises**, including of the wire surface (wire-permanence discipline in #14/#16 manages migration cost, it is not an outsider-facing guarantee). Testing cohort: Venkat alone on the two live nodes initially, possibly a few invited testers pre-1.0, no open beta. The session-11 RC bar (stable spec + 2 reference implementations) gates the 1.0 event itself. Recorded in `docs/roadmap.md` "Development-phase strategy" + the spec's status header.
22. **Namespace URI is a permanent opaque token** (session 15, 2026-09-11, Fable): `https://blygger.org/ns/0.1` never tracks the protocol version — the `0.1` is part of the token's spelling, fixed when the namespace was minted, not a version claim — and stays unchanged through every 0.x and the 1.0 release (Dublin Core `/1.1/`, Atom `2005` precedent). Closes a gap #14/#16 left open: those froze the other wire tokens (`blyg.json`, the `blyg:` prefix, the GUID scheme) but never covered the URI; `types.ts` asserted permanence in a comment ("once v0.2 ships importers") with no decision record, and that window closed silently at the session-13 deploys, leaving live feeds declaring `ns/0.1` against `blyg: "0.2"` manifests — which this decision makes *correct*, not a mismatch. Rationale: vocabulary evolution rides the ignore-unknown-`blyg:*` rule (spec §11.4) inside one namespace; a version-tracking URI would force readers to enumerate namespaces and break exactly the readers the ignore rule protects, and it would make the URI a *stricter* version signal than the deliberately informative manifest key (#18d) — the manifest's `blyg` key is the version signal, the URI is identity. A semantically incompatible future vocabulary would mint a new URI; reserved, expected never. Renaming to a version-free spelling (`/ns`) was considered and rejected: post-deploy the churn is real and the benefit cosmetic — the page served at the URI itself answers the confusion at the exact moment it arises. Recorded publicly in spec §7 + the `blygger.org/ns/0.1` page.
23. **Per-version spec documents; the highest version is the living one** (session 15, 2026-09-11, Fable + Venkat; amends #15's structure): each protocol version gets its own **standalone-complete** normative document (`docs/protocol-v{X.Y}.md` → `blygger.org/spec/{X.Y}/`) — a superset revision of the previous version's full text, never a delta: a `/spec/{version}/` URL hands an implementor one complete document. The **highest-numbered document is the living one**: testing-driven revisions (per #21) land only there; at the moment version N+1's document is published, version N's stops receiving edits, flips DRAFT → **SUPERSEDED** (forward-linking banner + index status), and stays citable with its snapshots intact. Rationale: the living-doc rule gives #21's "spec changes in response to testing" a single unambiguous home, and supersession keeps citations stable without pretending frozen text is current.
24. **Pinned-version HTML pages** (session 18, 2026-09-12, Fable + Venkat; amends the session-5 §2.8 ruling via the additive path it explicitly reserved): a publisher MAY serve a rendered page per pinned version at the live permalink + `/v{n}/` (`f/{id}/v{n}/`, `t/{id}/v{n}/`) — gated exactly like the JSON file (404 unless pinned, 200 forever once pinned, survives withdrawal), serving that version's publish-time `content_html` verbatim, with `rel="canonical"` to the live permalink, a frozen-snapshot banner, and a link to its `v{n}.json` twin. 25. **§8.4 constrains routes and promises, not presentation; the pinned-version carousel conforms** (session 20, 2026-09-13, Fable; resolves the session-19 flag): the 0.1 sentence "a public page's version display is an indicator, not navigation" was session 5's *rationale for refusing history routes*, not a UI mandate — a presentation mandate would contradict the protocol's own charter (invariant 1 "the protocol governs only the page"; §8.4's own "page chrome is presentation"; §10.5). The normative content, restated in `protocol-v0.2.md` §8.4 so the two readings can never diverge again: **no route serves unpinned history in any representation, and a version display MUST NOT offer, imply, or hint at access to unpinned versions** — every version exposed, by link or presented in place, must be one the origin already promises forever (live + pinned, nothing else). Within that bound, presentation is the client's; the design-intent sentence (pins are frozen citable artifacts of one identity, not pages of one document) is retained as guidance — keep each pinned version discrete, visibly frozen, individually citable. 26. **Cross-client transclusion and nesting** (session 22, 2026-09-16, Fable 5.1): the `![[id]]` grammar is unchanged; resolution order becomes **local published item of any kind → imported non-L0 blyg item by `remote_id` (current, or tombstone with a pin-retained snapshot) → error**, with more-than-one-imported-match a publish error rather than a guess — the directive names an *identity*, not an origin. **The local snapshot is what gets baked, never a live fetch**: publish does not depend on the network, quoting follows reading, and network cycles are harmless because snapshots are static bytes. 27. **Stubs are threads with `stub_of`; the stub action absorbs `respond`** (session 22, 2026-09-16, Fable 5.1): a stub is a thread declaring itself a response to **one** target via top-level `stub_of`, in two shapes — `{origin, id, version}` for a blyg target (`origin` REQUIRED even when own: a citation is absolute) or `{url}` for a plain-web target. Version-agreement rule: at publish, if the body transcludes the target, `stub_of.version` := the baked version, else it keeps the creation-time value. 28. **Webmention mechanics** (session 22, 2026-09-16, Fable 5.1; mechanism + verification principle were locked session 7): manifest key `"webmention"` (URL, origin-relative allowed; absent = does not receive; static exports omit it) plus W3C `rel="webmention"` link + `Link` header on pages; reference endpoint at `{origin}webmention` — *inside* the origin surface because it is a protocol surface, unlike host-rooted `/studio` and `/api`. **Send** on publish for every remote-origin reference (`stub_of`, `transclusions[].origin`, later `forked_from`); source = the item's permalink page, target = the referenced item's page; discovery = target manifest key first, W3C discovery second, none → `no_endpoint` (no retry); network/5xx/429 retry **15m → 1h → 4h → 12h → 24h** then failed; fire-and-forget from the author's view; republish re-sends only new/changed references; withdrawal re-sends once so the receiver can mark it gone. **Receive**: 400 on syntactic failure or unknown target item, 429 over 60/hour/source-host, 202 then async **structural verification** (≤ 2 fetches, ≤ 3 redirects, 5 s, 1 MB): source page → `rel="alternate" application/json` → item document (or JSON directly); the document's `origin` MUST equal the final source URL's origin (0.2 §12.2 applied inbound — kills mirrors and impostors); withdrawn → `gone`; relation from `stub_of` / `transclusions[]` / `forked_from` naming our origin + the target id, else failed. **No content is stored** — a verified mention is a pointer. Verified mentions are **studio signals** (detect-stubs), never auto-published, never on any protocol surface; public display is per-item curation under 0.2 §13.5 (Phase B, Venkat's call). Plain non-structural mentions: spec MAY, held apart as a lower class; **reference client drops them at 0.3**. Static-only deployments do nothing and stay conformant. Plan §2.3.

37. **Imported generated text is disclosed through the existing `generated[]`; the draft's rule 7 was wrong and is replaced** (session 27, 2026-09-28, Fable + Venkat; un-defers §8b's `impyrt`): the honesty-critical claim is *this prose is machine-generated*; who ran the model is not part of it, and the wire already refuses to carry how generation was asked for (#20). 38. **The protocol is agent-agnostic at every level, and says so; the response-versus-pipe line is what matters, not human-versus-agent** (session 27, 2026-09-28, Fable + Venkat): three attribution levels, each covered by an existing construct that never asks who acted — **span** (`generated[]` + `blyg-tk-gen`, whether a tool you invoked or an agent acting on its own; the difference is an unverifiable process claim), **item** (an agent is a valid opaque `author`; whole-item generation is one block span in `generated[]` — byline says who, provenance says how), **origin** (invariant 4: the only authenticated entity is the origin, and DNS is owned by someone accountable; invariant 3 is about the reader side and the wire, never about who writes). At the studio an agent is a third-party authoring tool with #31's scoped tokens — a peer is a token with a member's scopes, and the token does not know the difference. `tn-2` gets an **agent byline convention**: name, the agent's own URL, and an `operator` URL naming the accountable human/org. An agent that *reads and responds* to every member item under its own byline, disclosed as generated, is a legitimate stubber — a critic, not a planet; #36's anti-pattern is content-free stubbing whoever runs it. **Maintenance splits on the same line:** detection and ops (stale snapshots, withdrawn sources, pin checks, mention retries, upgrades) are client automation — crons, not a role; **anything that republishes is authorship**, because refreshing a snapshot bumps the version, emits a feed entry and re-sends a mention — snapshot independence exists so a quote stays what the author chose. An agent with refresh authority is a co-author with `update` scope; there is no safe maintenance-only scope. Wire fact worth keeping: **a re-bake is distinguishable from an edit** — same `content_hash`, new version — so a client can show "snapshots refreshed" and a narrower refresh scope is definable later on that identity. Recommended: detect always, refresh only on a decision, never silently. No "I am an agent" flag on the wire (a spammer would not set it; the honest agent is known by its origin). Plan §8c.

43. **Version boundary rule: revisions add what readers already ignore safely; a new version is needed when a reader or receiver must change what it does** (session 28, 2026-09-28, Fable 5.1; gives #21/#23 a test): a revision to the living document may add any construct a conformant reader of that version already handles correctly by the ignore-unknown rule, with no change in the meaning of what it does display — `cited`, `generator_url`, `[[id]]`'s rendered anchor, `changelog[].generated`, `origin` on `sources[]`. A new protocol version is required when a construct changes what a reader or receiver must *do* to be correct — a new mention relation a receiver must verify, a selector a reader must honour, a field that changes feed derivation. ## Model routing

Coding sessions run on **Opus** (Sonnet for small, fully specified tasks) working from the written specs in `docs/`. **Fable** rules what cannot be undone. **Since session 33 (2026-10-03, decision #58) the gate is blast radius, not topic**: Opus 5.5 rules a question itself when the answer is reversible, and stops for Fable when it is not.

**The four-question test.** Before stopping for Fable, Opus asks:

1. Does any reader, receiver or importer have to change to stay correct? (#43's own test.)
2. Does it add, remove or rename anything readers see — a document field, a `content_html` class, a `content_md` grammar form, a mention relation, a manifest key?
3. Does it narrow, widen or reinterpret a locked decision, or touch the Fable brief's do-not-open list?
4. Can Opus cite the locked decision whose principle already settles it?

**All no on 1–3 and a yes on 4: Opus rules.** Write the decision in the list below in the usual format — next number, bold headline, `(session N, date, Opus 5.5 — Fable review pending)`, the reasoning in the current plan doc's rulings section — then build. Promotions of a §16 shape into normative text after its gate has run are in this tier: move the text, fix the cross-references, add the §17 line, record the build's calls. **Any yes on 1–3, or no principle to cite: stop and tell Venkat**; a Fable round can rule the same afternoon. Fable reviews every Opus-ruled decision in batch at its next round, and strikes the pending label or reverses — a reversal in this tier costs one studio release, because nothing in it reaches the wire. Roadmap items still marked **⚠️ FABLE** are the ones where question 1 or 2 is a yes by construction (new versions, verification and identity semantics, crypto, public API surfaces, the spec freeze).

Everything else is implementation: do what the plan doc specifies; small local judgment calls (naming, file layout, error copy) are fine; what a build finds that the spec should say goes in the devlog's open threads.

## Stack conventions
