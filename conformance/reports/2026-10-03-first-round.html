0. The question these tools answer

A protocol can fail in three ways: the text disagrees with itself, a party disagrees with the text, or everyone follows the text and what you intended still doesn't happen. Conformance testing only catches the second. The third is the expensive one, and Brady Dale's report is the proof: "I had Codex check the spec and it said Blynger is doing everything the spec requires", yet his fork page told a visitor nothing. Codex was right about the clauses. The intent failed anyway.

So the toolkit has a piece for each kind of failure:

2. Where the rules don't guarantee what they're meant to model counterexamples

#FindingEvidenceTier
1Two blygs path-mounted on one host can verify mentions in each other's name. §15.4 step 2 compares scheme, host and port only, so example.com/alice/ passes as example.com/carol/. That's exactly decision #36's group shape, and #14 makes path mounts first-class. Fix, confirmed by the model: require the source URL to sit inside the claimed origin's full base URL.Alloy 7 / 7cFable
2A partial quote can be uncheckable from the moment it's published. One baked from a stale local import names a version its origin no longer serves, so §10.2's "any reader MAY re-check" never applies. The window also closes once the target is republished without a pin. Two live partial quotes are already in this state. This bears on your stated intent: "verifies that the quoted bit is actually part of the transcluded item".Alloy 6b, 6c; live crawlerFable
3The local closure check depends on which version it walks. If it follows each local thread's current transclusions[], a thread can contain itself (A v2 ⊃ C ⊃ B v1 ⊃ A v1). Walking the versions actually baked is safe. §10.2 doesn't say which.Alloy 1a′ (fail) vs 1a (pass)Fable
4A pinned copy of a stub keeps verifying after the stub is withdrawn. The pin file still carries stub_of, which contradicts §9's "a withdrawn stub stops verifying". Fix, confirmed by the model: verify against the live items/{id}.json.Alloy 7d / 7eFable
5The watermark should outlive the stored copy. If a reader deletes both on withdrawal (§13.4 says it SHOULD delete the copy), a stale cache replaying v1 is silently adopted as the item coming back.Alloy 4cFable
6#57 can republish withdrawn, unpinned words under a new id. C is unpinned, a pinned thread quotes C, C is withdrawn, the thread is forked, and the flattened quote republishes C's words. That's the "freeze this quote at the withdrawn version" §10.2 says is deliberately not offered. Either accept it explicitly or add a SHOULD to drop or mark such quotes.Alloy 5g (b)Fable
7Decision #43's boundary test has a blind spot. It asks whether readers must change, but a forker re-parses another blyg's content_md, so grammar forms travel between clients. #49 was classed as a revision on reader grounds. #57 closes this for forks of threads; the test itself should say it.Alloy 5c; property testsFable

7. What held confidence, not just problems

  • No route ever serves a version that wasn't promised (§8.4): every pinned version is served and every unpinned one returns 404, in the models, in studio and on the live network.
  • Readers converge after any history of dropped, reordered or duplicated feed entries, failures and garbled feeds, once the index is diffed (§13.2, #18a).
  • The watermark never silently regresses; rewrites are loud (§13.3, #18b), even against a blyg that rewrites its own history.
  • Withdrawal rolls to null except for pins (#18c). Snapshot independence (§10.4). Mirrors can't take a subscription's identity (§12.2, #17).
  • Content hashes, index agreement, feed GUIDs, withdrawal endcaps and every fork's pin check out across the live network.

Every Alloy "pass" is paired with a run proving the scenario can actually occur, so no pass is empty. Scopes are stated per check. A pass means "no counterexample within this scope", not "proven".

8. How to use it

  1. Set up once: bash conformance/editor/setup-profile.sh, then code --profile Blygger conformance/editor/blygger.code-workspace. It needs Node, Python 3, Graphviz and Java 17 (for Alloy); the script checks for them and says what's missing.
  2. Look: run the Conformance: open dashboard task. Start with the intent ledger: those intents are my reading of your words, so correct them in conformance/intents.json. That file is yours.
  3. Rerun: Conformance: run all, or one tool at a time. The Alloy model takes about 25 minutes, the property tests about 8, the rest a few minutes. Then python3 conformance/build_dashboard.py.
  4. After a ruling: rerun, and the dashboard shows the gap closing (§1 is the worked example). After a spec edit, the clause register keeps every clause ID stable.
  5. Other clients can run the same schema and grammar checks against their own code through conformance/schemas/ADAPTERS.md. That's the start of the public conformance suite (track 1.4, #48).
