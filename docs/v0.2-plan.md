# v0.2 "Roots" Implementation Plan — subscribe side

**Status: DESIGN COMPLETE (session 12, 2026-08-10, Fable). Implementation not
started.** This plan resolves the two ⚠️ FABLE items the roadmap assigns to
v0.2 — the resolution/autodiscovery mechanics (decision #14's consequence) and
the importer state machine — and specs the subscribe-side client deliverables
to Sonnet/Opus-implementable precision. Protocol-semantics decisions made here
are recorded as locked decisions #17–#18 in `CLAUDE.md`; the shapes in §2–§3
graduate to `docs/protocol-v0.2.md` when that spec is drafted (after the build,
same sequence as v0.1).

Inputs: `docs/protocol-v0.1.md` (normative L1), `docs/roadmap.md` v0.2 section,
`docs/proposals/curation-discovery-generation-proposal.md` §1–2 (make-public,
blogroll), locked decisions #1–#16.

## 1. Objective & non-goals

**Objective:** the network exists. A blyg client can be handed a URL, resolve
it to a blyg origin or a legacy RSS feed, subscribe, poll, roll up remote edits
and withdrawals correctly (fragments and threads), recover losslessly from any
outage via the archive index, and triage imports into hoppers — with a merged
reading feed and optional published blogroll. Exit state (roadmap): two blyg
clients following each other plus a legacy blog feed, all readable in one
merged feed, surviving simulated outages.

**Non-goals (deferred, do not build):**
- Stubs, cross-client transclusion, `forked_from`, thread nesting, webmention —
  all v0.3.
- Any generation/AI surface — v0.4.
- WebSub or any push mechanism — polling only; revisit post-1.0 (decision #13).
- UI polish — the studio surfaces here are deliberately utilitarian; the full
  UI refresh is deferred to v0.5 (session-11 decision, `roadmap.md`).
- Imported items never appear on the publisher's feed, in any form (decision
  #12). Nothing in this plan emits anything new on the publish side except the
  blogroll and one manifest key.

## 2. Protocol artifacts

### 2.1 Resolution algorithm (locked decision #17)

*Resolution*, not discovery: given a URL found out-of-band, determine what to
subscribe to. Deterministic, bounded (≤ 6 fetches), ordered. Input: any URL.
Output: `{ kind: "blyg", origin, manifest }` or `{ kind: "rss", feed_url }` or
failure.

1. **Normalize.** Parse; strip query and fragment. If the path does not end in
   `/`, append `/`. Call this the *candidate origin*. HTTPS is expected;
   readers MAY permit `http:` (local dev) but SHOULD warn.
2. **Direct probe.** `GET {candidate}blyg.json`. If it parses as a manifest
   (JSON object with a `"blyg"` version key) → **resolved as blyg**. Do not
   trust `Content-Type` (dumb static hosts misreport); parse-success is the
   test.
3. **Feed upgrade.** If the input URL itself returns XML that parses as
   RSS/Atom: if the channel carries `<blyg:manifest>` (§7 of the L1 spec),
   fetch that manifest → **resolved as blyg**. Otherwise hold the feed as the
   **L0 candidate** and continue (a later step may still find a manifest).
4. **rel probe.** If the input returned HTML, look for
   `<link rel="blyg" href="…">` — `href` is the **origin base URL** (not the
   manifest file; the manifest filename is protocol-fixed, so readers append
   `blyg.json`). Resolve href against the document URL, probe as in step 2.
   **One hop only** — a rel target's own HTML is never scanned (no recursive
   discovery, no loops). Readers MUST support the HTML `<link>` element;
   supporting an equivalent HTTP `Link` header is OPTIONAL.
5. **Conventional-mount probes.** At the input's scheme+host root, probe
   `/blyg/blyg.json` then `/blyg.json` (skipping any URL already probed).
   Courtesy fallback only — publishers MUST NOT rely on it (decision #14: the
   mount is free; these probes exist because `/blyg` is the reference default
   and root mounts are first-class).
6. **RSS fallback.** If no manifest was found: the L0 candidate from step 3,
   or standard RSS autodiscovery on the input's HTML
   (`rel="alternate" type="application/rss+xml"`), → **resolved as legacy L0
   feed**. Otherwise resolution fails with the list of URLs tried.

Rules:

- **Subscription identity = final fetch origin.** The origin recorded for the
  subscription is the URL the manifest was actually fetched from (minus
  `blyg.json`), after redirects. The manifest's self-asserted `site` is
  display-advisory only; if it disagrees with the fetch origin the reader
  SHOULD surface the discrepancy and MUST NOT adopt the asserted value as
  identity — otherwise a mirror could inherit another origin's identity,
  violating origin-scoping (§11.7). This is the subscribe-side face of
  "the only protocol-authenticated entity is the origin" (decision #11).
- **Redirects:** follow up to 5; the *final* URL wins as origin.
  Cross-host redirects are allowed (sites move); identity is where the bytes
  actually came from.
- `rel="blyg"` is used unregistered for now; registering it in the
  microformats existing-rel-values registry is a post-ship errand, not
  protocol-blocking.
- Re-resolution: readers MAY re-run resolution when a subscription's manifest
  404s persistently (the blyg may have moved and left a rel link); adopting a
  new origin is a **user-confirmed** action, never automatic (it is an
  identity change).

### 2.2 Blogroll (decision #13, mechanics finalized here)

- **Standard OPML 2.0, no extensions**, served at origin-relative
  `blogroll.opml` (wire filename, mount-independent, decision #14). Each
  entry: `type="rss"`, `xmlUrl` = the subscription's feed URL, `htmlUrl` =
  its origin (or page URL for L0 feeds), `text`/`title` = display title.
- No blyg-specific OPML attributes are needed: a crawler resolving `xmlUrl`
  through §2.1 gets the blyg upgrade for free via the `<blyg:manifest>`
  feed element (step 3). Plain OPML tooling keeps working untouched. This is
  the reuse-don't-invent play again — the wire already carries the upgrade
  path.
- Manifest gains an OPTIONAL `"blogroll"` key (origin-relative path,
  canonically `"blogroll.opml"`). Publishers SHOULD also emit
  `<link rel="blogroll" …>` on the HTML feed page.
- Publishing the blogroll is a publishing act: it is the curated *subset* of
  subscriptions the owner chose to show (per-subscription flag, default
  **off**). No completeness claim, ever (decision #13). A blyg with no public
  subscriptions serves no `blogroll.opml` (404) and omits the manifest key.

### 2.3 Version key policy (locked as part of decision #18)

Manifests and item documents emit the spec version their publisher implements:
a deployment serving 0.2 surfaces (blogroll key) emits `"blyg": "0.2"`.
Readers MUST accept any `0.x` value and apply the standing ignore-unknown
rules; the version key is informative, not a negotiation. (Breaking changes,
if ever, get a major bump and their own migration story — not this mechanism.)

## 3. Importer semantics (locked decision #18)

### 3.1 The reconciliation model

**The archive index is the reconciliation surface; the feed is a cheap
trigger.** `items/index.json` is complete by construction (§6.2: every item
ever, no window), so diffing it against local state is total reconciliation —
the feed's only jobs are cheap change detection and low-latency pickup of new
events. Consequences, which dissolve most edge cases structurally rather than
case-by-case:

- **Feed-window gaps** are not an error path: any suspected gap falls back to
  an index diff, which recovers everything regardless of how much window was
  missed.
- **Clock skew is irrelevant to correctness**: rollup is driven by version
  numbers (§11.2), never timestamps. Remote timestamps are display material.
- **Malformed feeds degrade, not corrupt**: an unparseable feed skips the
  trigger and goes straight to index diff; an unparseable *entry* is skipped
  individually (the containing feed is not rejected — the §11.4 ethos applied
  to syntax).

Three invariants govern all state transitions:

1. **The item document is ground truth for content** (§11.1). The feed never
   mutates item state directly — an interesting feed entry (including a
   withdrawal entry) triggers an item-document fetch, and only the fetched
   document advances state.
2. **The local version watermark never silently regresses.** The highest
   version ever observed per item is a monotonic watermark. A fetched document
   with a *lower* version than the watermark is a protocol violation by the
   origin (§5.2: versions increment by exactly 1 per publish) — the reader
   MUST NOT silently adopt it, SHOULD surface the discrepancy, and MAY offer a
   user-confirmed reset to origin state. Without this, a compromised or
   rolled-back origin memory-holes its own edit history invisibly;
   with it, history rewriting is at least *loud*.
3. **Retention past withdrawal follows the origin's own serving surface.**
   On a withdrawal endcap, a conforming reader rolls up to null and drops
   content (§11.3) — *except* content corresponding to a **pinned** version,
   which it MAY retain: the origin itself still serves that exact content
   forever (§8.1), so local retention never exceeds the origin's own promise.
   This resolves hopper-copy-vs-withdrawal cleanly (§3.4).

### 3.2 Poll cycle (per subscription)

1. Conditional `GET feed.xml` (`If-None-Match`/`If-Modified-Since`; store
   `ETag`/`Last-Modified`). `304` → done.
2. Parse leniently (per-entry salvage). For each entry carrying `blyg:id`,
   extract `(id, version)`; entries without `blyg:*` on a blyg subscription
   are ignored (L0 subscriptions instead take the wrapper path, §3.5).
3. **Trigger set** = entries whose `(id, version)` is unknown locally or
   ahead of the local watermark. For each, fetch the item document
   (`blyg:item` URL if present, else `{origin}items/{id}.json`) and run the
   transition function (§3.3).
4. **Gap check:** if the previous poll's newest-seen GUID is absent from the
   current window *and* the trigger set was non-empty, events may have
   scrolled out → run an **index reconciliation**: fetch `items/index.json`,
   diff `(id, version, updated)` against local state, fetch and process every
   changed item (bounded concurrency ~4). Also run index reconciliation:
   on first subscribe (initial backfill), after any poll failure recovery,
   and periodically regardless (SHOULD, e.g. every 24h — cheap insurance,
   one file).
5. Record `last_poll_at`, newest-seen GUID, and per-event `observed_at`.

Failures: network/HTTP/parse failure → exponential backoff
(min(2^fails × base, cap)); after K consecutive failures mark the
subscription `degraded` (visible in the subs UI, keeps retrying at the cap);
never auto-delete, never touch stored item state on poll failure. Honor
`Retry-After` on 429/503. A 404 on `items/index.json` from an otherwise-live
blyg means a nonconforming publisher: fall back to feed-window-only operation
and flag the subscription (lossy mode).

### 3.3 Item transition function

Inputs: fetched item document `D` (parsed, schema-tolerant per §11.4/§11.5),
local state `L ∈ { absent, current(v), tombstone(v) }` (tombstone = withdrawal
seen at version v; retains id + watermark, content gone).

| L | D | Transition |
|---|---|---|
| absent | kind ∈ {fragment, thread} | Import at `D.version`. |
| absent | kind = withdrawn | Record `tombstone(D.version)`. Nothing to import. |
| current(v), D.version > v | fragment/thread | Update stored copy to D; hopper copies update (§3.4). |
| current(v), D.version > v | withdrawn | Roll up to null: delete content, keep `tombstone(D.version)`; hopper entries → placeholder except pinned-backed (§3.4). |
| tombstone(v), D.version > v | fragment/thread | **The item returning** (§9): import as current. Re-imported normally. |
| current(v) or tombstone(v), D.version = v | same kind, same `content_hash` | No-op. |
| current(v), D.version = v | same kind, **different `content_hash`** | Stealth edit (no version bump — origin violation). Content ground truth wins: adopt D, but log a discrepancy signal on the subscription. Watermark unchanged. |
| any, D.version < watermark | any | **Regression** — invariant 2: keep local state, flag; surface after M consecutive polls; user-confirmed reset only. |
| any | unknown kind / unparseable | Ignore the document, flag; local state untouched (§11.4). |

Notes:
- `author` is carried verbatim, never rewritten (§5.5), scoped to the
  subscription's origin.
- Thread imports store the baked `content_html` and the `transclusions`
  provenance verbatim; readers never resolve directives (§10.2), so a thread
  import is content-wise identical to a fragment import plus provenance
  metadata.
- `content_hash` SHOULD be verified against `content_md` on import; mismatch
  = discrepancy signal (adopt content anyway — the hash is the origin's own
  claim about its own bytes; a mismatch is a defect report, not a security
  boundary at L1).
- Fetched `content_html` MUST be sanitized before rendering in the reading
  UI (§12) — sanitize at render, store verbatim (ground truth is preserved;
  presentation is defended).

### 3.4 Hoppers, snapshots, and withdrawal

- Hopper-add snapshots the item's current local copy; later imported versions
  **update** the snapshot (roadmap rule — hoppers track the living item, they
  are not pins).
- On withdrawal roll-up: hopper entries render as a "withdrawn by origin"
  placeholder and public hopper pages MUST stop displaying the content —
  **unless** the snapshot corresponds to a version the origin has pinned
  (fetchable `items/{id}/v{n}.json`), in which case retention and continued
  display (with attribution linking the pin) are conformant per invariant 3.
  The reference client checks for a pin covering the snapshot version at
  withdrawal-processing time (one fetch), and downgrades to placeholder if
  none exists.
- If the user wants a durable citation of someone else's content, the answer
  is the origin's pin, not a local hoard — consistent with the pin being the
  protocol's only immutability instrument (§8).
- Thumbs up/down are stored signals (table, §4.1), no protocol surface, no
  transmission anywhere.

### 3.5 L0 grandfathering (legacy RSS wrapper)

A plain-RSS subscription imports each entry as a **summary fragment + link**:

- Local synthetic id: derived deterministically from the feed's GUID (or link
  if no GUID) — origin-scoped like everything else; never a protocol blyg id,
  never exported.
- `content_md` = title as a link to the entry URL + the entry
  description/summary (sanitized, truncated ~2,000 chars to the fragment
  ethos); marked `l0` so the UI can badge it.
- RSS has no versions: same GUID reappearing with changed content is treated
  as an edit (local version bump). No withdrawal concept: entries scrolling
  out of the window are simply retained locally (an L0 feed has no index and
  no endcaps — the wrapper is best-effort by design).
- L0 items are hopper-able and appear in the merged feed like any import.

### 3.6 Merged reading feed ordering (client policy, not protocol)

Reverse-chron by display time = `min(claimed updated, observed_at)` — the
clamp means a future-dated or badly-skewed origin cannot pin itself to the
top of the reading feed forever; it sorts no newer than when we actually saw
it. Per §11.2 ordering across origins is explicitly the reader's own policy;
this is the reference client's.

## 4. Reference implementation architecture

Additions to the v0.1 worker (same stack: TS, Hono, D1, R2; same repo).
The poller runs on a Cloudflare **cron trigger**.

### 4.1 D1 schema (migration 0004)

```sql
CREATE TABLE subscriptions (
  id TEXT PRIMARY KEY,                -- local random key
  kind TEXT NOT NULL,                 -- 'blyg' | 'rss'
  origin TEXT NOT NULL,               -- blyg: origin base URL; rss: feed URL
  feed_url TEXT NOT NULL,
  title TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'active',  -- 'active' | 'paused' | 'degraded'
  etag TEXT, last_modified TEXT,
  last_poll_at TEXT, newest_guid TEXT,
  fail_count INTEGER NOT NULL DEFAULT 0,
  last_index_sync_at TEXT,
  in_blogroll INTEGER NOT NULL DEFAULT 0,
  flags TEXT NOT NULL DEFAULT '[]',   -- JSON discrepancy log (regression, stealth edit, hash mismatch, site-vs-origin, lossy-mode)
  created TEXT NOT NULL
);
CREATE TABLE imported_items (
  subscription_id TEXT NOT NULL,
  remote_id TEXT NOT NULL,            -- blyg id, or synthetic l0 id
  kind TEXT NOT NULL,                 -- 'fragment' | 'thread'
  state TEXT NOT NULL,                -- 'current' | 'tombstone'
  version INTEGER NOT NULL,           -- watermark (highest ever observed)
  created TEXT, updated TEXT,         -- origin-asserted
  observed_at TEXT NOT NULL,          -- ours; display clamp input
  content_md TEXT NOT NULL DEFAULT '',
  content_html TEXT NOT NULL DEFAULT '',
  content_hash TEXT,
  author_json TEXT, media_json TEXT, transclusions_json TEXT,
  l0 INTEGER NOT NULL DEFAULT 0,
  pinned_version_retained INTEGER,    -- non-null: tombstone whose content survives via this pinned version
  PRIMARY KEY (subscription_id, remote_id)
);
CREATE TABLE hoppers (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, slug TEXT UNIQUE,
  public INTEGER NOT NULL DEFAULT 0, created TEXT NOT NULL
);
CREATE TABLE hopper_items (
  hopper_id TEXT NOT NULL,
  subscription_id TEXT NOT NULL, remote_id TEXT NOT NULL,
  added_at TEXT NOT NULL,
  PRIMARY KEY (hopper_id, subscription_id, remote_id)
);
CREATE TABLE signals (
  subscription_id TEXT NOT NULL, remote_id TEXT NOT NULL,
  thumb INTEGER NOT NULL,             -- 1 | -1
  at TEXT NOT NULL,
  PRIMARY KEY (subscription_id, remote_id)
);
```

v0.2 hoppers hold **imported items only**; v0.3 extends membership to own
items when threads compose from hoppers. Deleting a subscription cascades its
imports, hopper memberships, and signals (local data only; nothing was ever
re-emitted, so nothing public is affected).

### 4.2 Routes

**Public** (only two new surfaces — both mount-relative):
| Route | Serves |
|---|---|
| `GET /blyg/blogroll.opml` | §2.2; 404 when no subscription is flagged public |
| `GET /blyg/h/{slug}/` | Public hopper page: snapshots + source attribution + origin links; only for `public=1` hoppers (decision #12 — curation display, never feed re-emission) |

Manifest: add `"blogroll"` key when the blogroll is non-empty.

**Studio** (cookie auth): `GET /studio/subs` (list + add-by-URL form +
per-sub status/flags/blogroll toggle), `GET /studio/reading` (merged feed,
§3.6 order, hopper/thumb affordances), `GET /studio/hoppers`,
`GET /studio/hoppers/{id}`.

**API** (cookie auth): `POST /api/subscriptions` (body `{url}` — runs §2.1
resolution; returns resolved identity for confirm, or the probe trail on
failure), `DELETE /api/subscriptions/{id}`, `POST /api/subscriptions/{id}/
pause|resume|resync` (resync = force index reconciliation),
`PUT /api/subscriptions/{id}` (blogroll flag, title override),
`POST /api/hoppers`, `PUT/DELETE /api/hoppers/{id}`,
`PUT/DELETE /api/hoppers/{id}/items/{sub}/{remote_id}`,
`PUT /api/signals/{sub}/{remote_id}` (body `{thumb}`).

**Cron**: `scheduled()` handler — every 15 min, poll subscriptions due
(default interval 30 min per sub, jittered; backoff per §3.2). All fetches
set a distinct `User-Agent` (`blyg-ref/0.2 (+https://blygger.org)`).

### 4.3 Testing the state machine

The §3.3 transition table is implemented as a pure function
(`importer/transition.ts`: `(local, fetchedDoc) → {next, effects, flags}`)
so the table is testable without any network: table-driven tests enumerate
every row plus the edge cells (regression, stealth edit, tombstone return,
unknown kind, hash mismatch). Poll/gap/backfill logic is tested against
fixture feeds + indexes served from test bindings. The simulated-outage exit
criterion (§6) is an integration test: scripted publish sequence on node A,
subscriber B offline past the feed window, reconnect, assert lossless
convergence via index reconciliation.

## 6. Definition of done

Roadmap exit criteria, restated concretely: the two live nodes
(`venkateshrao.com/blyg/`, `blyg.protocol-institute.org`) subscribe to each
other and to one legacy RSS feed; edits and a withdrawal on one node roll up
correctly on the other; a subscriber kept offline past the feed window
catches up losslessly via index reconciliation (verified item-by-item); the
merged reading feed renders all three sources; a public hopper page and a
blogroll are live on at least one node; 0 test failures.

## 7. Open decisions (Venkat)

   due-based) is the plan's default; tune freely, no protocol impact.
2. **First-subscribe import depth** — this plan imports the full archive
