> the 0.4 document is published, and every ruled 0.4 shape appears in its §16 first
> (decision #42). This file is the design record: what 0.4 is, what it is not, and why.

**Status:** defined, Fable 5.1, session 28 (2026-09-28). Decisions **#43–#50** in
`CLAUDE.md`. No open questions. No 0.4 document exists yet, on purpose (§5).

## 1. What a version is, now (decision #43)

Pre-1.0 every version is a draft (#21) and the highest-numbered document is the living
one and receives revisions (#23). That left a question the 0.3 freeze made concrete:
what makes a construct a *revision* to the living document rather than the start of
the next version? The answer is a test, not a list:

- **A revision** may add anything a conformant reader of that version already handles
  correctly under the ignore-unknown rule, with no change in the meaning of what it
  does display. `cited`, `generator_url`, the anchor `[[id]]` renders to,
  `changelog[].generated`, `origin` on `sources[]`, and — corrected the same afternoon,
  §2.2 — a partial-quotation `selector`, since readers display baked HTML and never
  resolve. All revisions.
- **A new version** is needed when a construct changes what a reader or receiver must
  *do* to be correct: a mention relation a receiver must verify, a field that changes
  feed derivation, a construct a reader must interpret to display content at all.

Consequences: the 0.4 document is opened when the first construct of the second kind
is built and exercised across two nodes; 0.3 flips to SUPERSEDED at 0.4's publication;
until then 0.3 §16 carries the shapes. Two living drafts is one too many.

## 2. The wire in 0.4

### 2.1 Remote generation sources (decision #44) — ruled in full

The question from session 26: may a TK source come from another blyg, and if a
generator is fed a stranger's words, is that a *source* or a *quotation*?

**A source.** Decision #20 drew its line by the authorial act — verbatim-and-visible
is a quotation, drawn-upon-and-woven is a source — and the origin of the words does
not move that line. A blockquote around non-verbatim prose would be false.

**And it notifies.** The tempting alternative was silence, by analogy with `[[id]]`.
But #32 kept links silent for a reason that cuts the other way here: notification in
this protocol tracks whether the *target's words are carried*. A link carries none. A
generation source carries them, transformed. A silent rule would make
paraphrase-by-model the one way to use a stranger's words without telling them —
exactly backwards for a medium whose premise is citations that can be checked.

The shape (0.3 §16.3, buildable now):

| Part | Rule |
|---|---|
| `generated[].sources[]` entry | The §5.9 reference: `id`, `version`, `origin` (present for remote, omitted for own — every existing document stays valid). MAY carry `cited`. Four constructs, one reference object. |
| Resolution | At generation time, by §10.2's order: local published item → imported item with a current or pin-retained snapshot → error; more than one imported match is an error. Sources widen from own fragments to **any item a directive may name, threads included**. |
| What is fed | The **local snapshot**, never a live fetch. Generating follows reading, as quoting does. |
| Disclosure | **Direct only**, as §10.3 for transclusion. A thread fed as a source is disclosed as that thread; what it had baked is inspectable through it. |
| Mention | A remote source is a remote reference and SHOULD send a mention with relation **`source`**. Verification (§15.4) gains a fourth clause; the set becomes `stub \| transclusion \| fork \| source`. A 0.3 receiver reports it `failed`, which is correct for a 0.3 receiver. |
| HTML | Nothing beyond the existing `blyg-tk-gen` wrapper. Span-level source mapping stays unpromised. |

**Cost accepted.** An agent that draws on thirty remote items sends thirty mentions.
That is legitimate under #36, whose anti-pattern is *content-free* stubbing: each of
these mentions says a model at this origin used those words, and the item it points at
has content. It is also the signal an author in an AI-native medium most wants.

**Why Fable wrote this before a build.** The project's rule is testing precedes prose
(#21). This construct cannot be built until the wire can say it — the client's
`ScopeProvenance.sources` has no `origin` — so the shape had to come first. It enters
normative text only after blygger-studio ships it and the two nodes exercise it, and
that exercise is what opens the 0.4 document (§5).

### 2.2 Partial quotation (decision #49) — ruled, and it is a 0.3 revision

**Venkat's case:** the commonest publishing norm in blogging — link an item and quote a
suitable block of it as the inspiration. More extensive quotation is commentary (the
stub with a whole transclusion) or fork territory. That gives the medium three registers
of borrowing, and the protocol already had two; the missing rung is the small one and
should be the same construct as the whole form with a selector.

| Part | Rule |
|---|---|
| Grammar | A transclusion directive immediately followed, no blank line, by a markdown blockquote is a partial transclusion; the blockquote's text is the selection. A blank line detaches. Chosen over `![[id\|passage]]` for readability and multi-paragraph quotes. |
| Faithfulness | Selection MUST be a substring of the target snapshot's text content (rendered HTML, tags stripped, whitespace collapsed per block, block boundaries as line breaks) at publish, else publish error. Readers MAY re-check while the version is served. Same condition as the whole form plus a substring test; elision is not fixed and not claimed. |
| Wire | `transclusions[]` entry gains OPTIONAL `selector` — `exact` REQUIRED, `prefix`/`suffix` OPTIONAL and short (W3C text-quote shape). Verification ignores it. Relation `transclusion`; staleness unchanged. |
| Bake | `class="blyg-transclusion blyg-partial"`; inline formatting vs plain text left to the build. |
| Cap | None. |
| Plain-web `{url}` targets | Nothing: ordinary markdown blockquote, no versioned document to verify against. |
| Studio | Select text in the reading view → quote; the stub action prefills this form for long targets. |

**Why a revision, not 0.4.** §1's first draft named "a selector a reader must honour" as
the paradigm of a new-version construct. On this protocol's own terms that was wrong:
readers never resolve, they display baked HTML, and a 0.3 reader that ignores `selector`
displays the passage correctly, runs the same staleness check and receives the same
relation. Nothing a reader or receiver does changes, so #43 says revision. Recorded as
a correction because the rule gave an answer its author did not expect, which is what a
rule is for. **Consequence: 0.4 opens on remote generation sources alone.**

### 2.3 The manifest locates the surface (decision #51) — adopted from a public proposal

[blygger-spec#2](https://github.com/blygger/blygger-spec/issues/2) (cyberscribe,
2026-09-27) made a case the project had not measured: managed hosts intercept `.json`
and `.xml` paths as static files before a CMS routes them, so WordPress — the largest
CMS on the web — cannot serve §4's fixed paths without rewrite rules that shared hosting
often forbids. §4's rule was written for filesystem-shaped deployments.

**What the fixed-filename rule protects** (#14) is that a reader handed a bare origin
finds the manifest with no HTML. That covers `blyg.json` only. The manifest already names
`feed` and `items`; §4 merely forbade readers from trusting the values, a rule that was
never doing work.

| Part | Rule |
|---|---|
| `feed`, `items` | Authoritative. Origin-relative or absolute; defaults `feed.xml`, `items/index.json`. |
| `item`, `pin` | New OPTIONAL RFC 6570 level-1 templates: `item` with `{id}` (default `items/{id}.json`), `pin` with `{id}`,`{n}` (default `items/{id}/v{n}.json`). Readers MUST expand them. |
| Discovery | §12.1 step 2 unchanged (`blyg.json` at a bare origin, always first). Step 4 extended: fetch the `rel="blyg"` href; if it parses as a manifest, that is the manifest; else append `blyg.json`. No new rel, no new media type. |
| Identity | The manifest's final URL minus its last path segment (§12.2 restated without the filename). Must be stable, since every reference names it. |
| `page` | MAY be absolute. |
| Unchanged | Static-file conformance; feed elements (already absolute); mount independence; receivers check targets against their own templates. |
| Not adopted | `rel="alternate" type="application/blyg+json"` — a second discovery vocabulary for a job the existing link does. |

**Why 0.4.** A reader that ignores the template keys 404s on a templated blyg, so what a
reader must do changes (#43). **Cost:** following a reference needs the target origin's
manifest to expand `item`; subscribed readers hold it, receivers own theirs, so the only
new fetch is one cached manifest per unknown origin on a staleness check.

**Gate for normative text:** one client not written by this project publishing through
templates — the WordPress case, whose proposer is the likely builder — and the reference
client subscribing to it, transcluding from it, and sending it a mention that verifies.

## 5. What 0.4 is not, and sequencing

Everything the roadmap's original "Canopy" paragraph named besides the two items in
§2 is **client work under Track 2** and needs no protocol text: staleness detection
and bulk re-pin (#33), auto-hoppers and the filter plugin interface, the reference
agent (#39), generated changelog notes (#40 — its `changelog[].generated` member is a
**0.3 revision** when built, by #43), the discovery surfaces (#41), `impyrt` (#37).

**Sequencing under #21, #23, #42:**

1. Shapes live in `protocol-v0.3.md` §16 now (done, session 28).
2. blygger-studio builds remote generation sources against §16.3 and the reader side of
   §16.6e (§7.5); both nodes exercise remote sources — a TK scope on one draws on the other's item, the far side verifies `source`,
   the generated prose imports with provenance intact.
3. `protocol-v0.4.md` is opened at that point as a standalone superset of the 0.3 text,
   0.3 section numbers preserved, §16.3 promoted into §5.7 and §15.4. Partial
   transclusion (#49) is a 0.3 revision and enters whichever document is living when it
   is built.
4. Published via `sync_spec.py` (0.4 `DRAFT`, 0.3 → `("SUPERSEDED", "0.4")`); first
   snapshot the same day.

**Exit criterion for 0.4:** step 2's exercise, live, on both nodes; and §2.3's gate — a
templated third-party blyg the reference client can subscribe to, quote, and mention.

## 7. Implementation plan (Opus/Sonnet-safe; written session 28 against blygger-studio at `f28c054`)

Two constructs, both additive, **neither needs a migration**: `versions.transclusions`,
`versions.generated_json` and `items.tk_provenance_json` are JSON text, and
`mentions_in.relation` is an unconstrained TEXT column. Every existing document and row
stays valid. `PROTOCOL_VERSION` moves to `"0.4"` only with the release that ships §7.2 —
partial transclusion (§7.3) is a 0.3 revision and ships without a bump. Each task is a
commit-sized unit with its acceptance check; semantics are fixed by #44 and #49 and the
spec's §16.3/§16.4 — if the build finds a case they do not cover, record it in the devlog
open threads and stop rather than improvise.

### 7.3 Partial transclusion (decision #49) — a 0.3 revision

- **P1 — grammar, in `walk()`.** After a `DIRECTIVE_LINE` match, look ahead: if the very
  next line begins with `>` (no blank line between), collect the run of consecutive `>`
  lines as the **attached blockquote**; a `>` line that is empty after the marker is a
  paragraph break inside the selection; the run ends at the first line not beginning with
  `>`. A blank line after the directive detaches. `extractDirectives` (used by previews of
  unpublished drafts) must consume the attached blockquote too, and `previewTransclusions`
  renders the partial form. *Acceptance:* `threads.test.ts` — attached vs detached, a
  directive followed by a blank line then a blockquote bakes a whole transclusion plus the
  author's own quote unchanged.
- **P2 — the normalizer, written once.** `selectionText(html)` in `markdown.ts`: like
  `plainTextFromHtml` but block boundaries become `\n`, whitespace inside a line collapses
  to one space, lines are trimmed and empty lines dropped. The selection side is the
  attached blockquote's markdown rendered to HTML and passed through the **same**
  function, so inline markdown in the quote matches the target's rendered text. Export it;
  the read-side re-check (a future studio surface) must call this and nothing else.
  *Acceptance:* unit tests in `util.test.ts` or a new `selection.test.ts` — nested blocks,
  entities, emphasis, a `<br>`.
- **P3 — the check.** `selectionText(target.contentHtml).includes(selection)` else fail
  with reason `quoted passage not found in the target's version N`. Record `prefix` and
  `suffix` as up to 32 characters either side of the **first** match (present only when
  non-empty). *Acceptance:* pass, fail, multi-paragraph pass, a quote that matches only
  after whitespace collapsing passes, a quote straddling two blocks passes because the
  boundary is a line break on both sides.
- **P4 — the bake.** `<blockquote class="blyg-transclusion blyg-partial" data-blyg-id
  data-blyg-version [data-blyg-origin]>` containing one `<p>` per selection line, text
  escaped. **Build call, recorded here in advance:** plain text in paragraphs, not the
  source's inline HTML — the selection is defined on text, and carving an HTML sub-range
  faithfully is a second project. Reverse this only with a reason written in the devlog.
  *Acceptance:* the whole-form bake is byte-identical to before (the 0.2/0.3 shape
  assertion in `cross-client.test.ts` stays as it is).
- **P5 — provenance and the rest.** The `transclusions[]` entry gains
  `selector: { exact, prefix?, suffix? }`; `Transclusion` in `types.ts` gets the optional
  member. `remoteReferences` needs no change (a remote partial is a remote transclusion);
  `relationTo` needs no change (it ignores `selector`); `applyVersionAgreement` needs no
  change (a stub whose body partially quotes its target still agrees on version).
  *Acceptance:* `tk-emission`/`threads` tests assert the entry shape; `mentions.test.ts`
  proves a partial remote quote verifies as `transclusion`.
- **P6 — import.** Assert, not assume: an imported document whose `content_html` carries
  `blockquote.blyg-transclusion.blyg-partial` keeps both classes and the data attributes
  through `sanitizeHtml`, and the reading view renders it as a quote. *Acceptance:* one
  test in `test/importer/`.
- **P7 — studio.** Two affordances, exact UX yours: (a) **select-to-quote** in the reading
  view — with text selected on an entry, a "quote" action opens the stub composer prefilled
  with `![[id]]` and the selection as an attached blockquote; (b) the **stub action's
  prefill** for a long target (suggest: selection text over ~600 characters) prefills the
  directive plus an empty `> ` line and focuses it, instead of quoting the whole item. The
  preview shows the partial bake and the not-found error before publish. *Acceptance:*
  behaviour tests on what the handlers produce, not just that buttons render (house rule).
- **P8 — the CSS contract and the spec.** `blyg-partial` becomes a permanent wire token
  when §16.4 is promoted. That promotion, and the `css-contract.md` line, are the Fable
  session's — say in your devlog entry that both nodes have exercised it (P9) and it gets
  written.
- **P9 — the cross-node exercise.** On the PI node, a stub of a venkateshrao thread whose
  body quotes one paragraph of it. Check and record: (a) PI's document carries the
  `selector` entry and the `blyg-partial` bake; (b) venkateshrao's mentions view shows it
  verified as `stub`; (c) venkateshrao's reading view shows the partial quote after
  import; (d) a deliberately wrong quote is refused at publish with the reason above.

Do **§7.3 first** — smaller, no version bump, and it lands in the living 0.3 as soon as
Fable promotes it — then **§7.2**, whose release carries the `0.4` bump and opens the

**Done** means: 0 test failures; `tsc` clean; the static export byte-identical to served
routes on both nodes for every pre-existing item; both exercises (R8, P9) run live on the
two nodes with their ids recorded in the devlog; `CHANGELOG.md` entries for each
release stating `Migrations: none`; and the studio backlog ticked with what the build
found, including the P4 call if it was reversed.

### 7.5 The manifest locates the surface (decision #51) — reader side in the studio

The publisher side is someone else's build (a WordPress plugin, per the proposer); the
reference client's own surface keeps the default paths and **emits no template keys** —
absent means default, and emitting defaults would only make every manifest longer. What
the studio must do is *read* templated blygs:

- **M1 — manifest model.** Parse `feed`, `items`, `item`, `pin` from a fetched manifest
  with defaults; store the four resolved values (or templates) on the subscription row.
  One expansion helper for RFC 6570 level 1 — `{id}` and `{n}` only, percent-encoding per
  the RFC — used everywhere the importer, the staleness check (#33), `[[id]]` resolution
  of a remote page, and mention verification construct an item or pin URL. *Acceptance:*
  unit tests for expansion; a grep shows no remaining literal `items/${"{"}id}.json`
  construction outside the helper.
- **M2 — resolution.** `importer/resolve.ts` step 4: fetch the `rel="blyg"` href; if it
  parses as a manifest, resolved; else append `blyg.json`. Identity = manifest URL minus
  its last segment (today's code assumes the segment is `blyg.json`; make the rule
  general). *Acceptance:* `test/importer/` fixtures for a manifest at
  `/wp-json/blyg/v1/manifest` discovered from HTML, with templated item and pin URLs,
  absolute `page`; the identity origin asserted as `/wp-json/blyg/v1/`.
- **M3 — receivers.** `targetItemId` in `mentions/receive.ts` matches a target against
  our own `page` and item path only (we emit defaults), so it needs no change — assert
  that with a test rather than assume it. **Amended session 38 (#61):** `verifyMention`
  *does* change. After #61 it requires the source document's final URL to equal
  `{origin}items/{id}.json`; a templated sender (Soapbox serves item documents under
  `/wp-json/`, identity `/blyg/`) fails that. When the URL does not match the default,
  fetch the asserted origin's `blyg.json` (bounds raised to 3 fetches), expand its `item`
  template with the document's `id`, and accept on an exact match; otherwise fail.
  *Acceptance:* a Soapbox-shaped fixture verifies; the same document served from a

### 8.1 Kyle Mathews' phase 3 — OAuth and MCP (decision #52)

The question was whether an OAuth rollout and an MCP server (his `migration.md` §3) go
beyond #31 and #39. **They do not, with four invariants.** #31 fixed the *token model* —
bearer, coarse verb scopes, owner-minted and owner-revoked, the root password held by
no tool — and said nothing about how a token is minted. Micropub, the tradition #31
cites, authenticates with IndieAuth, which is OAuth 2 with your own site as the
authorization server. A flow in which the tool sends the owner to their own studio to
approve scopes is therefore the tradition itself; a paste-a-token page is the other way
to mint the same token, and both must exist (a cron or the reference agent has no
browser). Refresh tokens, a token endpoint and redirect handling are client contract by
#31 ¶3.

What made this a blessing rather than a refusal is the measured state of the ecosystem.
Blygger Desktop holds either the owner password (signs in at `/studio/login` on a stock
server and keeps the password in the Keychain) or a single unscoped `BLYG_OWNER_TOKEN`
Worker secret on an extended one — both are exactly what #31 exists to end — its author
lists the scopes he needs in studio#11 and says he switches the day scoped tokens ship,
and his server docs already describe upstream's OAuth plan as the thing that replaces
both. Two auth systems would have been the outcome of fighting the plan; one is the
outcome of constraining it.

The invariants, which double as the review checklist for the PR:

1. **One token model.** OAuth mints #31's tokens: scoped, listed, revocable per token and
   all at once, in the studio. The password is typed only on the studio's own login page.
   The manual mint-and-paste path exists beside the flow.
2. **No `.well-known`, no manifest key.** `/.well-known/` is host-rooted and would break a
   path-mounted blyg (#14); discovery is the HTML `rel` link on the studio page, and the
   metadata it points at lives under the mount. Nothing about auth reaches `blyg.json` or
   the spec.
3. **Scopes:** a read scope for studio-private material (#39b); publishing a distinct verb
   from drafting; no refresh-only scope (#38). Names are the build's.
4. **MCP** is the same operations under the same scopes, authenticated with a token like
   any other tool. Text an agent writes through it is disclosed through client-recorded
   provenance (#37's path; the `tk-provenance` route in studio#11) with `sources` in the
   §5.9 shape. Polling, not webhooks (#39c). It is a transport for the client's contract,
   not the agent contract: `tn-5` still comes from the reference agent.

Consequences: Opus queue item 2 is withdrawn and the contributor builds 2.9 in his phase
3; password reset rides with his auth middleware; Opus reviews the PR against the four
invariants and drafts `tn-4` once gate G3 opens. Upstreaming Blygger Desktop's reading

## 9. Rulings after the fork round (session 33, 2026-10-03, Fable 5.1)

### 9.1 A fork of a thread flattens its quotes (decision #57)

**The report.** Forking a thread that itself quotes other items gave an editable top
level and, one level down, `![[id]]` directives that could not be edited. Venkat's
proposal: recursively unroll the whole tree and flatten it. His alternative, raised and
set aside: a thing may be pinned only if everything it transcludes is pinned.

**The defect under the report.** `createFork` copies the pinned version's `content_md`,
and in the source a quote exists only as a directive. So the fork inherits a
*composition*, which re-resolves in the forker's context at publish (§10.2): an
own-origin fork quotes the fragment as it is now, not as v1 baked it; a remote fork fails
at publish for each quoted origin the forker is not subscribed to and drifts for the rest;
and the fork sends `transclusion` mentions to third parties on the forker's behalf, a
composition act the forker never chose. `fork.ts` says a fork must descend from "the bytes
anyone else can still fetch." It did not.

**Why pin-closure is wrong.** Not tedium, though it is tedious and impossible for imported
sources. A thread's pin already freezes every baked quote in its `content_html`, nested
ones included. The fragments' own pins add nothing to the promise. The quoted bytes are
promised by the thread's pin, which is why flattening can be sourced from the pin alone,
with no network and no local resolution.

**The shape** (spec §16.6f; promoted to §5.6 rule 6 in the eleventh revision, session 39):

| Part | Rule |
|---|---|
| Source of quoted text | The pinned file's `content_html`, never the forker's local snapshots. |
| Own prose | Byte-exact from the pinned `content_md`; only quoted material goes through HTML-to-markdown, which is tractable for this dialect. |
| Each quote | An ordinary markdown blockquote of the `blyg-transclusion` element's content, recursively (nested quotes nest), plus a visible attribution line: origin, id, link to `page` where the node can compute it, else the item document. `blyg-partial` flattens from its baked paragraphs. |
| Wire token | `blyg-transclusion` MUST NOT survive; the forker baked and verified nothing. The quote is in the plain-web register: editable, linked, unverified. Lineage is the way to verify. |
| Provenance | No inherited `transclusions[]`, no quote-mentions. A live quote is re-cited by hand with `![[id]]`; the editor can make that one click per block. |
| Generated spans | `blyg-tk-gen` in own prose and in quotes re-wrapped as `impyrt`, so `generated[]` survives. Today's fork drops it for a forked fragment too — the restore-then-publish class of leak (session 32). One re-wrap fixes both. |
| The precise instrument | Forking a quoted fragment directly, naming its own pin, is still how to own one passage with its own lineage. |

**Classification.** Publisher behaviour with no wire change: a revision by #43. Strict #21:
§16.6f now, §5.6 rule 6 after the build and a cross-node exercise (a fork, on one node, of
a thread on the other that quotes a third item). Gate **G11**; Opus queue item 5.

### 9.2 TK sources, clarified (no ruling)

Three questions from the same session, all answered by #44 and #32 as they stand:

- **Imported sources inside a scope** report "unresolvable" because `resolveFragment`
  keeps the v0.1 rule: local, published, fragment-only. #44 already widened it to any item
  a directive may name, resolved by §10.2's order against the local snapshot. The build is
  G8 (§7.2, R2 replaces that function), deferred by Venkat at session 32 and still deferred.
- **What goes out** is not the scope. Nothing of the grammar reaches the wire (§5.7 rule
  2 forbids the instruction in provenance): the output as prose, wrapped `blyg-tk-gen`; a
  `generated[]` entry naming each source by reference; at 0.4, a `source` mention for a
  remote one. The source's words are never carried as a quote (§5.7 rule 3). "TK
  transclude" is therefore a misnomer the docs should avoid: it names the one thing the
  construct is defined not to be.
- **`[[id]]`, `[text](url)` and bare URLs inside a scope are literal text.** The scanner
  treats only `![[id]]` as a source. The model receives the string and the surrounding
  document, never the target's content; nothing is fetched, nothing disclosed. Correct by
  the principle shared by #32 and #44 — disclosure and notification track whether the
  target's words are carried — and resting on the generator being network-free, which it
  is and must stay.
- **One edge** for the studio: a `![[id]]` left in the *output* on its own line is, at
  publish, a real transclusion with the quote wrapper — and a source only if the instruction
  also named it (corrected session 38, decision #60; this bullet first said "both"). Consistent,
  since the author left it there; the studio warns when an output contains a directive the
  instruction did not. Folded into Opus queue item 5.

### 11.2 The label — `[[id | text]]`, `![[id | text]]` (decision #70; queue items 17 and 19)

Three requests met here. Venkat (session 48) wanted to write a link's anchor text himself.
Ned Twigg ([blygger-spec#16](https://github.com/blygger/blygger-spec/issues/16)) wanted
*copy ID* to hand him `[[id - title]]` so that a thread source assembled from ids is
readable — which is a request about **directives**, not links. And studio#20 proposed
`[[text]]` for tangling, a span to be minted as a fragment at publish.

**One construct answers the first two.** In either bracket form the id MAY be followed by
a pipe and a label. On a link the label is the anchor text the publisher bakes; on a
directive it is a comment and reaches nothing. Resolution ignores it in both cases, so the
id alone names the target and a 0.3 publisher sees literal text. The label is the author's
words, not a claim about the target — the same stance as `cited` (§5.9), frozen at the
moment of reference — so the protocol checks nothing, and a client that wants to warn when
a label drifts is being courteous, not conformant. No escape sequence: a label that needs
`]]` is rewritten. A label may contain a pipe, because the id is positional and the first
pipe after it is the separator.

**Order.** Venkat asked for `[[title | id]]`, and I had first ruled id-first on parser
grounds (every bracket form puts the id right after `[[`, including the reserved
`![[id@vN]]`). He restated his preference as "wiki convention", then stated the principle
that decides it: received conventions trump cosmetic preference, and the project departs
from them only for a technical reason (#71). The double-bracket convention is target-first
— `[[Page|label]]` in MediaWiki, `[[note|alias]]` in Obsidian, whose `![[…]]` embed this
grammar already borrowed; Roam, Logseq and Notion have no pipe form at all (Roam and Logseq
alias with a markdown link around the ref, Notion inserts a mention object with no text
syntax). Label-first lives in other bracket families: markdown's `[text](url)`,
TiddlyWiki's `[[Label|Target]]`, Confluence's `[label|link]`. So the principle, applied
with the fact corrected, gives `[[id | text]]`. Recorded at this length because the order
was reversed twice in one afternoon, and the reason it settled where it did is the
principle, not the parser.

**Tangling gets no construct.** Its published output is ordinary wire (the thread holds
`![[id]]` directives after the rewrite), so the protocol has nothing to say about its
spelling — except the rule that now tells the two proposals apart: any `[[…]]` whose first
26 characters are not an id is literal text on the wire, and a client-private authoring
form inside brackets MUST be rewritten before publish, by the principle that keeps
generation instructions off the wire (§5.7). Under that rule tangling is the studio's
decision. My recommendation to it, not a ruling: do not spell tangling `[[text]]`, because
with #70 in the grammar a `[[text]]` whose author forgot the id would silently mint a
fragment whose content is the label. A distinct sigil costs nothing.

**Version.** The label travels in `content_md`, which readers see, so #58 question 2 routes
it to Fable; by #43 it is revision-grade, since readers display `content_html` and a
flattened fork link (#63) carries the baked anchor text, which is now the label. It lands
in 0.4 because 0.4 is the living text, not because it needed a version.

**Interactions checked.** #46 (no title field): the label is anchor text, not a title, and
§10.1 already called anchor text presentation. #54: inert inside code, as both forms are.
#63: a fork flattens the link to `[label](absolute page)`; a 0.3 flattener that does not
know the form takes the whole-HTML rebuild path rule 6 already allows. #43: the grammar is
written down for a publisher re-parsing another's `content_md`. Item 21: unaffected,
since generated output is not grammar (§11.4).

### 11.3 Received conventions trump cosmetic preference (decision #71)

### 12.2 `cid` on pinned entries (decision #74, blygger-spec#13)

The proposal's instinct is right: a pin is a promise the origin can fail to keep by
losing its host, and a CID is the only way a third party can hold the bytes and prove
them. Two of its three open points — deterministic CIDs across tools, and media on other
hosts — come from making the referent a *bundle*. One file has neither problem: the CID
names the pinned document's bytes as served, and media is already immutable by URL
(§5.4), so a mirror can fetch it. The third open point — retention or re-emission — is
answered by §13.4's own principle: retention follows the origin's serving surface, and a
pinned file is served forever, so mirroring it never exceeds the origin's promise;
mirroring unpinned versions does, and is forbidden. The cost accepted: a publisher that
emits `cid` gives up §8 rule 6's freedom to assert `author` at serve time for that file.
The pin-log contract and the CID profile are deliberately a technical note: the protocol
says what the member means, not how a particular network computes it.

Under #71 the question is not whether `{width=…}` is pretty but whether a received
convention exists, and one does: Pandoc's link attributes, which markdown-it-attrs

### 12.5 `ignyr` (decision #77)

Venkat's directive (session 34) wanted feed consumers to be able to shelve trivial
versions — refresh republishes, batches of them — and he ruled (session 43) that the name
stays and that an agent's refreshes carry it by default, leaving "where it lives" to
Fable. The recommendation on file was an OPTIONAL boolean on the changelog entry. That is
a version-significance marker — the thing #19 and TN-1 refuse, argued at length: a cheap
flag beside a bare counter, which authors would route around and readers would learn to
distrust. The refusal was written against "this version matters *more*"; it holds for
"matters *less*" by the same argument.

The wire already carries the fact. A refresh republish changes `content_html` (new bakes)
and not `content_md`, so its `content_hash` equals the previous version's — §16.6b named
this as the way a client tells a re-bake from an edit without any construct. A subscriber
holds the previous hash. So the rule is a reader rule in §13.2: same hash as the version
before it is maintenance; MAY queue low; SHOULD NOT resurface as new. Both of Venkat's
rulings survive: the studio's queue is called *ignyr*, and an agent's refreshes land in it
by construction, not by declaration. What is lost is a signal to plain RSS readers; they
see every version as new already (per-version GUIDs, §7), and a flag they would have to
learn is not a smaller change than the one refused. Venkat was told this runs against the
shape he had assumed, and said to record it.

## 14. Rulings of session 50 (2026-10-19, Fable 5.1): simple responses and significance

Venkat opened with "there is demand for simple responses" and three questions; a fourth
came from a parallel Opus session rigging an `ignyr` word into changelog notes. Five
decisions, #79–#83, written into the 0.4 text's **fourth revision** (not snapshotted).
One additive wire change: the `links[]` member and the `data-blyg-label` attribute.

### 14.1 Links notify (decision #79, reversing #32)

Forks have sent mentions since 0.3, so the live half of the question was `[[id]]`. #32
made it silent on purpose — "the one way to cite without notifying" — and #50 built on
that premise. Venkat asked for the reversal explicitly. The structure that makes it safe:

- **A wire member, because nothing else is verifiable.** Without one, the receiver would
  have to scan HTML for the target URL, which is the trackback check §15.6 already
  demotes. So each resolved link produces a `links[]` entry, `{id, origin?}`, not a
  reference: a page, not a version.
- **The receiver derives the relation**, `link`, last in §15.4's order. Nothing can be
  "stated in the webmention" — a sender's claim is never trusted. What Venkat called
  "ignyr implied" lands as the receiver-side **notice** class (§14.2).
- **The silent citation survives as the markdown link.** `[text](absolute page URL)`
  renders to the same anchor and produces nothing on the wire. The author chooses by
  spelling: the bracket form is this protocol's citation, the URL is the web's. That is
  what keeps #32's affordance while meeting the demand, and it is why #50's condition on
  the reader affordance ("copy `[[id]]`", never "respond") still stands: a link is still
  not a response, it is now a disclosed one.
- A fragment reading `[[id | this]] is right` is the simple response the medium lacked,
  without touching #27: stubs stay threads.
- Version: additive member, readers ignore unknown members, revision-grade by #43, the
  same path `source` took. A 0.3 receiver fails `link` mentions, correctly. Forks flatten
  the bracket form (#63), so a fork carries no entry for an inherited link — one-hop
  custody (#65).

### 14.2 Reposts and the two classes of mention (decision #80)

Venkat asked whether a bare `![[id]]` is a SHOULD NOT. It is not: the studio ships it as
the repost shape (0.31.0's 2×2 plus "repost, no words"), and §10.6's misuse paragraph is
about stubbing everything with nothing to say. He wanted it treated like a link on the
receiver. Ruled so, with no wire marker — a sender's "this matters less" is what #19 and
#77 refuse, and the wire already says it: a repost's `content_md` is nothing but
directives. The receiver strips directive lines, attached selection blockquotes, labels
and whitespace; nothing left is a repost. The relation is unchanged (stub-ness is the
marker's, §10.6 rule 2); the **class** changes. §15.5 now has **responses** (`stub`,
`transclusion`, `fork`, `source`, with words) and **notices** (`link`, reposts): held
apart, never in a responses list, shown if at all as "linked from" / "reposted by", routed
to a low-priority queue — the studio's ignyr; the protocol says *notice*.

Venkat then asked how a thread with many directives knows what it responds to. The wire
answers: a response is a stub and has exactly one target (§10.6 rule 1); every other
remote directive is a quotation with its own `transclusion` mention; the receiver decides
per relation, the repost test per document. A client's only choice is the wording in its
list.

### 14.3 The directive label travels (decision #81)

Venkat wanted `![[id | text]]`'s label to be the link title, "since transcludes also
present with links". Premise corrected: the bake has no link inside (§10.2); the "quoted
from" line is presentation, so a subscriber never had the label. The publisher's own page
could already use it; to reach subscribers and fork flatteners it must be in the bake, as
`data-blyg-label` on the blockquote, RECOMMENDED as the attribution anchor. One
definition now covers both forms. Guarded against #46: a reader MUST NOT present it as the
target's title or as anything but the quoter's words; it is frozen with the quoted version
and checked by nobody, as `cited` is.

### 14.4 Responding from anywhere (decision #82)

How does a human stub an item from a browsing view on any device, and must there be a
subscription? §10.2 step 2 said "from any subscribed origin" — a client-local notion
(#13, §10.6 rule 7) that had leaked into a wire rule. It now reads: any snapshot the
publisher holds from the item's identity origin by §12, by polling or by a one-off fetch.
The recommended client shape is one deep link that takes a URL, resolves it, holds a
one-off snapshot with no subscription, and opens the composer as `stub ↗` does — reached
by bookmarklet, share sheet and browser extension alike. Two things flagged: the studio's
`imported_items` is keyed on `subscription_id`, so one-off snapshots need a store with
retention rules of their own; and a client-agnostic "stub this" on a blyg page must find a
stranger's studio, which is a convention across clients and therefore an RFC (session-40
rule), not a ruling — the received pattern is a registered `web+blyg:` handler with a
Mastodon-style remote-interaction fallback. Queued as item 23; drafted when Venkat says go.

### 14.5 Significance marking (decision #83)

Opus, in a parallel session, read #77 as forbidding an `ignyr` token in changelog notes
and asked for a ruling. Opus was right. A word in free text that readers route on is the
flag #77 refused with a worse spec (`[skip ci]` is the precedent); the moment readers
honour it, authors write it at them. "Matters less" has its own attack: publish a strong
claim, then soften it under "ignyr" so subscribers do not re-read — the rewrite §13.3
guards against. Wikipedia's minor-edit flag, the received convention, works because one
origin has admins who sanction misuse; across origins nobody can. So: TN-1 already makes
the note the home of human-readable significance, and writing "ignyr" there is allowed as
prose; §5.2 now says no token in a note has wire meaning (the #70 sentence, for notes).
The honest author lever is **not publishing** — a change not worth an event waits for the
next one; held revisions are studio sugar. And the reader rule that catches
content-bearing trivia without any claim is **near-sameness**: #77 keys on an identical
hash, edit distance zero; the reader holds the previous `content_md` at reconciliation and
can measure the change, so §13.2 lets a version under a reader-local, never-advertised
threshold be maintenance too. Keep it small — one word can negate a sentence — and
nothing is ever omitted, only queued.

## 15. Ruling of session 52 (2026-10-20, Fable 5.1): the mention target is known by membership (decision #84)

Robert Peake, whose WordPress plugin Soapbox publishes the one templated blyg in the
field, reported ([blygger-spec#17](https://github.com/blygger/blygger-spec/issues/17))
that §15.3 step 1 — the target "MUST lie within this blyg's own origin, the full base
URL, not merely its host" — rejects every target a templated blyg itself names. On
robertpeake.com the base URL is `/blyg/`, the pages are WordPress permalinks at the site
root (§5.8 allows an absolute `page`) and the item documents are under
`/wp-json/soapbox-blyg/v1/` (§6.1 lets the manifest relocate them). The reference client's
mention to that blyg on 2026-10-07 verified only because Soapbox had already read the
clause as membership rather than location.

The finding is correct, and the record shows how the text got there. The "full base URL"
wording came from the session-38 conformance round: Alloy check 7 found that §15.4 step
2's *source* check compared scheme, host and port only, so two path-mounted blygs on one
host could verify in each other's name, and its note added that "§15.3's target check has
the same scheme/host/port shape and should be read the same way" (#61). The analogy was
wrong, because the two checks answer different questions. Step 2 asks whether a stranger's
document really comes from the origin it claims; the receiver knows nothing about that
origin except where the bytes were served from, so location is the only authority, and
#61 stands exactly as written. Step 1 asks whether a URL is one of *the receiver's own*
items; the receiver owns that data, so membership is the authority and location was only
ever a proxy for it — one that §5.8 and §6.1 broke the moment 0.4 let a publisher put
an item's addresses outside its base URL.

**Ruled.** The target MUST resolve, by the receiver's own published data, to one of this
blyg's items: an address the receiver itself serves for that item — its `page`, its item
document (own `item` template or the default) or a pinned version's document or page
(§8, own `pin` template or the default). Location is not the test, and neither is the
host: with an absolute `page` a CMS may put permalinks on another host, a host test would
reject that legitimate target, and it adds no protection membership does not give. Two
blygs on one host stay apart by the same test — a target is one blyg's item or it is not —
which is the anti-impostor purpose the clause had, served directly rather than by proxy.
The 400-not-404 and withdrawn-target sentences are unchanged. The principle written into
the text so it survives the next relocation construct: **a receiver's own items are known
by membership; a stranger's document is known by where it was served.**

Pinned-version addresses are included deliberately. §15.2's reference sender always
targets the live page, but a third-party sender that forked "a pinned version of the
target" may reasonably name the pin, and refusing a correct-in-spirit claim with a 400
buys nothing; the mention is recorded against the item, never a version, as §15.4 step 5
already does. This is the one receiver change in the revision: the reference client's
`targetItemId` accepts `f/`, `t/` and `items/{id}.json` under its mount and must gain
the pin shapes. Its mount-prefix check is correct for it only because its surface is never
relocated — conformant by accident, which the spec now says in as many words so that a
client copying the shape knows what it is copying.

Grade: a revision in 0.4 by #43 — no wire change, a correction of text that contradicted
§5.8 and §6.1, plus one strict widening of what a receiver accepts. Not snapshotted.
Follow-ups for Opus: the studio's pin branch and re-anchored comment; the Alloy check-7
note in `conformance/alloy/checks.py`, which generalized #61 to the target side; C-15.3-01
re-extracts at the next clause build.

### 15.1 The sender's fallback target is the item document (decision #85)

Robert Peake's follow-up on #17, two hours after the fifth revision: §15.2 still told a
sender without the target's `page` to use "the reference convention" (`f/{id}/`,
`t/{id}/`), which the revised §15.3 refuses at any receiver that does not serve that
convention. He proposed the target's item document by its `item` template, since the
sender already holds the manifest from endpoint discovery and the item document is an
address every receiver serves.

The defect predates #84. §4 has said since 0.3 that the permalink paths are "a convention,
not a requirement" and that readers MUST NOT infer anything from the mount; a sender
guessing them does on the wire what §4 forbids readers to do. The old location test in
§15.3 hid it, because a default-layout studio happens to serve the convention. #84 exposed
it twice at once: Soapbox refuses the guess correctly, and the studio's own 0.48.1 kind
check refuses a thread guessed as a fragment — which `remotePermalink` in `send.ts` does
whenever it does not know the kind. The decisive case is §5.8's: "a blyg with no HTML pages
at all is still a blyg". It has no `page` and no convention; its item document is its only
mentionable address, so the item-document fallback is not merely more robust but the only
one that is always correct.

**Ruled.** Target = `origin` + `page` when the sender holds it; otherwise the item
document, expanded from the target origin's `item` template or the default (§6.1). A sender
MUST NOT construct a target from the permalink convention. `page` stays the first choice
because the receiver resolves both to the item, so it costs nothing, and the page is what
every live sender sends today and what a W3C-shaped log reads as a citation; only the guess
changes. `{url}` stubs and receivers are untouched — §15.3 already accepts the item
document for either kind. Revision by #43, sixth of 0.4, not snapshotted. Third-party
senders using the convention keep landing on default-layout studios except in the
wrong-kind case, and should switch. Studio: 0.48.2 sends the item document URL through the
target's `item` template whenever it lacks `page` (Opus brief item v).

### 16.1 Hopper feeds and the `hoppers` manifest key (decision #86, blygger-spec#18)

Aneesh Sathe's proposal, written for the World Machines bridge, which wants to subscribe
to members' public hoppers rather than to their whole blygs; it unparked queue item 14,
whose trigger ("a second client, or blygger.com, asking to discover hoppers by machine")
was met from a third direction. The proposal asked four questions and found one thing:
under §12.1 as written no hopper URL can resolve to a hopper, because step 2 or step 5
finds the member's manifest first and step 6 never runs.

**Where #12's line sits.** The decision's stated reason for refusing re-emission is
mechanical — collision with `blyg:id` rollup and the single-publisher invariant — and both
live in the state plane and the `blyg:` namespace. The manifest is not the state plane: it
already names a curated list, the blogroll (#13), and nobody has called that re-emission.
§13.5's "no manifest vocabulary" was written against a different question — whether an
imported item becomes a protocol object when displayed — and the answer to that is still
no: the feed names memberships, not items, and publicity stays a property of the list.
Item 14's original wording, "a list of links is not a re-emission", was right.

**The four answers.** (a) Not re-emission, on the condition the proposal itself proposes:
no `blyg:` namespace anywhere in the feed, own items included. The second draft's
recommendation on own items is confirmed for a sharper reason than rollup collision: a
hopper feed that carries `blyg:id` on own items is a *filtered blyg feed*, a partial
notification plane for the origin, and that is a different and refused construct. One rule
added that the proposal implies and does not state — **no item document ever names a
hopper**. Membership belongs to the list. That sentence is what keeps #12's "hoppers are
the taxonomy, not tags" true on the wire after this ruling. (b) Manifest-listed, step 7 as a
post-condition on steps 2–5, the manifest as authority exactly as #51 made it for `feed`
and `items`. No channel marker (a new wire element any feed could carry until checked
against the manifest anyway) and no reorder (identity would change for every legacy
input). Identity is (origin, the feed's resolved absolute URL), not "as the manifest names
it". (c) Excerpts, never the held snapshot: §13.5's own word, and the full snapshot would
make the curator a mirror of other people's text. RSS 2.0's `<source>` is the received
element for attribution (#71). (d) L0 rows scoped to the hopper subscription; absence is
meaningful because the feed is the whole list, so an entry that leaves MUST be dropped —
the one place this differs from §13.6. Following an entry's link through §12 is a separate
act with its own identity. One MAY added for the obvious case: a reader already holding the
item an entry links to may show it once.

### 16.2 The fixed name holds at every identity origin (decision #87, blygger-spec#21)

chrisbodhi's report: §4 says `blyg.json` at the origin; §12.1 step 4 and §12.2's
`/wp-json/blyg/v1/manifest` example describe an origin where it is not; §15.3, §15.2 and
§5.6 rule 2 assume it is. Tested live against a static origin reachable only through
`rel="blyg"`: Studio 0.48.2 forks from it using the surface it stored at resolution, blygd
refuses the fork and names the missing file. Two conforming clients, two answers.

**#51 contradicted itself.** It allowed a manifest with no address at the fixed name and
then costed reference-following at "one cached fetch per unknown origin" of the target's
manifest — a fetch that assumes `{identity}blyg.json` answers. The reporter named the three
parties who hold only an identity: a receiver verifying under templates, a sender building a
target (#85), a forker checking a pin. All three probe the fixed name, and the text told
them to. **Ruled as proposed:** `{identity}blyg.json` MUST serve the manifest, as the
manifest itself or by a redirect whose final URL has the same identity. Step 4's direct
form stays as discovery.

**Why the MUST is meetable** by the publishers #51 was for. The hosts that intercept `.json`
paths do so to serve static files; a CMS plugin can write one, and the directory holding it
is then the identity origin while the templates relocate everything else. Soapbox already
does exactly this — identity `https://www.robertpeake.com/blyg/`, `blyg.json` there, every
other surface under `/wp-json/soapbox-blyg/v1/` — so the one live templated publisher
conforms today. The publisher excluded is one that can neither route a `.json` path nor
write a static file, and that publisher was always going to struggle to serve a blyg.

**Not taken.** A `manifest` URL beside `origin` in every §5.9 reference: it bloats every
citation to repair a publisher's omission, and the identity rule would still have to be
checked against it. "Such an origin is readable only by its subscribers": it documents
silent breakage — the publisher's own mentions fail verification at every receiver — instead
of ending it. Revision by #43 (seventh of 0.4): publisher-side, readers already probe the
fixed name. #51 amended inline. Conformance: the publisher suite's probe of the fixed name
at the identity is a MUST.

### 16.3 Origin succession — the redirect and `moved_from` (decision #88, blygger-studio#102)

Florian Lohse moved `https://florianlohse.com/blyg/` to `https://blyg.florianlohse.com/`
on 2026-10-25, redirecting the manifest, feed and pages and leaving `items/**` static. His
pre-move subscribers kept reading — §12.2 keeps identity where it was — and were never told.
Venkat's thread then stubbed a post-move fragment under the old identity; the new Studio
refuses the target (outside its origin) and the relation (`stub_of.origin` is not its own),
so the response was lost on both sides. The reader-side fix is studio work; the question
here was whether a move has any wire statement.

**It has two, and both are already shaped.** (1) The old origin's permanent redirect of its
manifest is the statement of succession. Only its controller can issue it, which is
invariant 4's trust basis unchanged, and HTTP already has the word for it (#71), so no
`moved_to` key. (2) The successor acknowledges in its own manifest: OPTIONAL `moved_from`,
an array of former identity origins. The received pattern is Mastodon's `movedTo` plus
`alsoKnownAs` (and DID Core's `alsoKnownAs`); the narrower name is a technical choice, not
taste — "also known as" includes concurrent aliases, and a concurrent alias is exactly the
mirror §12.2 forbids. A reader offers to follow only when it has both; a redirect without
acknowledgement is reported as a discrepancy under the `site` rule §12.2 already has.
Adoption stays user-confirmed and never automatic.

**What `moved_from` does for receivers** is the half that recovers Florian's case without
anyone republishing: an origin in the receiver's own `moved_from` is read as naming the
receiver — membership by its own published data, #84's principle — with the target matched
after substituting its identity for the former one, which works because the mover kept
origin-relative paths (and SHOULD). The relation check accepts the former origin. A
receiver that ignores the key fails such mentions, as every receiver does today, so this is
additive.

**Why a self-asserted key is safe.** It proves nothing alone and gains an impostor nothing:
senders discover endpoints from the identity they hold, so a false `moved_from` never
attracts a mention, and a receiver that widens what it accepts as aimed at itself harms only
itself. The redirect, which only the old controller can set, is the proof; the key is the
acknowledgement that stops a misconfigured redirect from offering a merge.

**Publishers that move** SHOULD redirect the manifest permanently, SHOULD redirect the rest
of the surface, and SHOULD keep serving the item documents they published at the old
origin, because pinned bytes carry the old `origin` and §8 promised those bytes. Senders
change nothing: published references stay as made, a republish re-resolves against the
reader's current record and MAY re-send. Not opened: #11 (people), #12. New manifest key,
0.4 by #43, §16.13 as a ruled shape; gate is Florian's live case — his node declares
`moved_from`, Venkat's mention verifies, one reader is offered the follow. The directory's
two entries for his blyg (old and new origin, both listed 2026-11-01) are the same question
on blygger.com's side, for Opus.
