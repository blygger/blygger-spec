# v0.5 plan — Level 3, feature one: sealed content and permissions

**Written:** session 66 (2026-11-12), Fable 5.2, from a design round with Venkat.
**Status:** a design direction, agreed in the round and **not yet a locked decision**.
Nothing here is normative and nothing is built. **For:** Opus, to turn into RFC-6.
**Amended:** session 67 (2026-11-12), Fable 5.2 with Venkat (decision #104): five additions
to the RFC-6 direction (§3.1 `about`, §3.6 the pass, §3.7 challenges, §3.8 epochs, §3.9

beside RFC-6, and a worked example in §12.

reviewed this session (one correction, in R1's header).

## 0. Sequence

Level 3 arrives as two features, each with its own RFC.

1. **RFC-6, sealed content and permissions** (this plan). Encrypted content on the
   wire, and the way a reader gets a key: already holding it, asking for it, and being
   approved or refused by rule, by a person, or by a person's AI delegate. **No payment.**
2. **RFC-7, payments** (direction in §8; drafted beside RFC-6 since session 67). Payment
   as one more ground on which a key is granted. It adds **no wire construct of its own**:
   everything it needs on the wire is in RFC-6 (§3.1, §3.6–§3.9). It is a recommendation
   for how homes and readers do payments, and becomes a technical note at its close like
   any RFC (#90). RFC-6 becomes a note too, and in addition feeds the 0.5 document when
   its constructs are built.

The path for RFC-6, per #66 and #90: Opus drafts `docs/rfcs/rfc-6-sealed-content.md`
from this plan → Fable edits and rules → it publishes on blyg.blygger.org with a comment
period on Venkat's word → at close Fable revises, rules, and promotes it as a technical
note → **then** the studio builds, and the 0.5 document opens when the first construct is
built and exercised (#21, #43). Nothing is built in the studio before the close, except
a throwaway probe if Venkat says so (§10).

## 1. The use case

Ordinary information sharing inside an organisation, **with no assumed structure**.
Anybody can publish to the eligible population, to any segment of it, and decide for each
segment who is pre-approved, who is approved or refused automatically, and what goes to a
person as an exception.

- The first user is the Protocol Institute, a decentralised organisation **without
  single sign-on**. Sign-on may be used where it exists; it must never be required.
- A traditional organisation with one shared set of permission groups and a decentralised
  one where every node keeps its own must both fit, without the protocol knowing which it
  is looking at.
- Requesting access across organisations and across different clients is in scope.
- Redaction is a main case: a phrase inside a sentence, sealed to a narrower group than
  the sentence around it.

## 2. Vocabulary

| Term | Meaning |
|---|---|
| **Sealed entry** | One piece of encrypted content in an item document: ciphertext plus the wrapped key(s) that open it. |
| **Cover** | The readable text that stands where sealed content is, written by the author ("the acquirer", "restricted"). It is ordinary published content. |
| **Entry key** | The key that decrypts one entry. Fresh whenever the sealed content changes, so it is per version. |
| **Lock** | An opaque random id naming a **lock key**. Holding the lock key is standing membership: it unwraps every entry key wrapped under that lock. Roughly a standing permission group, except that the member list is never on the wire. |
| **Home** | The URL where a lock's keys are asked for. Not necessarily on the publishing origin. |
| **Grant** | A key (a lock key or one entry key) wrapped to a recipient (an origin's public key, or another lock's key). |
| **Ladder** | The private rules at a lock's home that decide a request: pre-approved, automatic yes, automatic no, or ask a person or their delegate. |
| **About** | Optional plain text on a sealed entry saying what is sealed. The seller's own claim. Not the cover. |
| **Epoch** | One generation of a lock's key. The lock id is stable; each epoch has its own key. |
| **Pass** | A bare public key a reader's client generates, used as a grant recipient by a reader with no origin. A bearer instrument. |
| **Terms** | A reference to a stable document stating the terms under which a key is held or content is offered. A citation, never enforcement. |
| **Door** | A lock's or an entry's request URL when it answers with a payment challenge. |
| **Voucher** | Opaque proof of a payment made elsewhere, presented to a home as evidence. |

Two grant sizes exist and the difference matters throughout: **the lock key** (standing
membership, past and future) and **one entry key** (a single exception).

## 3. What goes on the wire

Field names below are illustrative. The RFC proposes names; Fable rules them.

### 3.1 The `sealed` member and the cover

An item document gains one OPTIONAL member, a list of sealed entries. Level 2 readers
ignore it (§13.1) and read the cover, so every sealed item is still a valid document and
a valid feed entry (#4).

```json
"content_md": "There is an acquisition offer from the acquirer.",
"sealed": [
  { "entry": "e1",
    "wraps": [ { "lock": "k7f3…", "home": "https://keys.example/", "key": "<entry key wrapped under the lock key>" } ],
    "nonce": "…", "ct": "…" }
]
```

- **`content_md` carries only covers and clear text. No new markup.** This is the
  two-plane pattern of generated text (#20): marker-free source, a list in the item
  document, and a baked wrapper class in `content_html`.
- **`content_html` wraps each cover in a new permanent class**, working name
  `blyg-sealed`, with an attribute naming its entry. A reader holding the key replaces
  the cover with the decrypted content; everyone else shows the cover. The class is a
  wire token like `blyg-transclusion` and `blyg-tk-gen`.
- **`content_hash` stays what it is**: the hash of `content_md`, which is what a reader
  without a key reads.
- The studio's authoring mark for a sealed span is studio-private, as the generation
  grammar is, and never reaches the wire.
- **An entry MAY carry `about`** (session 67): plain text describing what is sealed, for a
  person or an agent deciding whether to ask or to buy. It is separate from the cover:
  the cover stands in the prose, `about` describes. Free text only — no tags, categories,
  price or structured fields — plain like a label (#102), capped (the RFC proposes a
  number), self-asserted and unverifiable before the key is held. It is never the item's
  title (#46) and a reader MUST NOT present it as one. **For a fully sealed item** the
  cover is the whole `content_md` and is the natural abstract, so `about` is usually
  absent; an author may use both (a teaser as cover, a factual description in `about`).
  **One rule for a reader or agent: `about` if present, else the cover.**
- **An entry carries a commitment** (item 2 of §9) and the proposal is that it also binds
  the description the reader saw — `about`, or the cover at that version when `about` is
  absent — so a buyer can show what was advertised against what was delivered.

### 3.2 Three granularities, one mechanism

| Granularity | Shape |
|---|---|
| Whole item | A **sealed item**: the cover is the whole of the required content members; one entry holds the body. |
| A block or a phrase | A **sealed span** inside any item. Not an item: no id, no version, no feed event of its own. |
| A block that deserves its own identity | A sealed item, quoted with the existing `![[id]]` directive. |

A sealed item is the case where one span covers the whole body. There is no third kind
and no change to the kinds.

### 3.3 Nesting

An entry's plaintext is itself content and may carry sealed entries of its own, to any
depth, under any locks. The inner entries sit inside the outer ciphertext.

- **Nesting is containment (AND).** A reader needs the outer key to learn that an inner
  entry exists.
- **"More restrictive" is the author's intent, not something the protocol checks.**
  Locks are independent. A client SHOULD warn when an inner lock has members the outer
  one lacks.

### 3.4 Several wraps on one entry (OR)

An entry may carry its key wrapped under several locks. Any one opens it; a reader that
holds more than one uses any, and the choice is local and unobservable. So locks compose
by OR within an entry and by AND through nesting.

### 3.5 Quoting sealed content

- A thread that quotes a sealed item carries a sealed copy of the quoted version, tied to
  that quote, with the item's cover as the visible text. Snapshot independence (§10.4)
  is kept: the copy does not depend on the source afterwards.
- **The quoter needs no key.** The ciphertext and its wraps are copied as they stand.
  Redactions survive quoting, and key holders still see through.
- Quoting a sealed item into a thread for another audience does not widen who can read
  it. Audience travels with the lock, not with the context.
- A span is bound to its document. A passage that should be reusable is made an item.

### 3.6 Origin keys and grant files

- **An origin may publish one public key in its manifest.** It is the origin's, never an
  author's, and it is for encryption only (§7).
- **A grant is a static file** holding a key wrapped to its recipient, at a path only
  the granter and the recipient can compute (derived from a secret they share and the
  lock or entry id). The reader probes with an ordinary GET: present means granted.
  Nobody else can tell which paths exist for whom, and there is no listing.
- **Recipients are of three sorts** (the third added session 67): an origin (its manifest
  key), a lock (the grant is wrapped under that lock's key), or a **pass** — a bare
  public key the reader's client generates and sends with a request. A pass gives a
  reader with no origin a static, re-fetchable grant with no account: the path is
  computable only by the home and the pass holder, and the home learns a key and nothing
  else. It is a bearer instrument: whoever holds the private key holds the entitlement,
  it can be handed over, and it can be copied, which is no worse than a shared key and
  must be said. The pass uses the same curve as origin keys; a wallet's or a token's
  control of a pass is evidence for the ladder, never a second key type on the wire.
  Of the first two: The second is a **lock-to-lock grant**: every holder of
  lock A also reads everything under lock B. This is how an organisation expresses its
  own ordering ("the board reads whatever the C-suite reads") with no hierarchy on the
  wire.
- A refusal may be delivered the same way: a file at the same path holding a sealed note.

### 3.7 The request endpoint

A lock's home answers requests for keys. It is a second dynamic surface, OPTIONAL like
the Webmention receiver; a static-only publisher issues grants by hand or uses a home run
by someone else.

- **Plain HTTP, one URL per lock and one per entry.**
- **Three answers**: granted (the key, or a statement that a grant file now exists),
  pending (decide later; the requester polls the grant path), refused (optional note).
- A request names the requester's origin and may carry a note and any evidence the home
  accepts, a sign-on token among them. The home wraps any grant to the key in that
  origin's manifest, so a false claim of origin earns a file the claimant cannot open.
- What the ladder contains, who is on which roster, and how a person or delegate is
  consulted are private to the home.
- **A home MAY answer with any HTTP challenge** (session 67): 401, 402, whatever scheme it
  likes. The protocol names none. A reader that cannot satisfy a challenge treats the
  request as not granted. A request that names no recipient is a probe; **the first
  answer to a probe is the same for everyone**, which settles §9 item 12 in the direction
  of "not an oracle" and lets that answer be cached.
- **The request names its recipient**: an origin, or a pass. The live answer carries the
  key wrapped to that recipient, and the home SHOULD also write the grant file, so the
  key can be fetched again without paying or asking again.

### 3.8 Epochs (session 67)

Rotation is made explicit, because a renewing subscription needs a stable thing to
subscribe to.

- **A lock has a stable id and numbered epochs**, each with its own key. A wrap names the
  lock and the epoch. Grant paths are derived per lock and epoch.
- When an epoch ends and what a period is are the home's. Only the number is on the wire.
- **Standing access** is a standing claim on the lock: each new epoch's key is granted to
  the recipient while the home's ladder says so (a roster, a paid subscription).
- **A reader keeps what it could read.** A recipient no longer granted new epochs still
  holds the old epoch keys. This is §5's revocation, restated; cutting off the past
  would be the rental refused in §8.
- **Whether the past is included** is a lock-to-lock grant from an epoch to the one
  before it, at the home's choice and invisible on the wire.

### 3.9 Terms (session 67)

There is no rights or licence construct anywhere in the 0.4 text. Level 3 needs one
(NDAs, officer disclosures, what a buyer is buying), and so does a public blyg that wants
to say "CC-BY". One construct serves all of them: **a reference to a stable document.**

- **Shape: the two shapes `stub_of` already has.** `{origin, id, version}` naming a blyg
  item at a version, or `{url}` for a document off Blygger (a Creative Commons deed, a
  legal page, a PDF).
- **A blyg target SHOULD be a pinned version.** Unpinned history is never served (§8.4),
  so once terms are revised an unpinned earlier version cannot be fetched by anyone. A
  pin keeps those bytes, with their hash, forever. A studio should pin a terms thread
  when it is first used.
- **Where it attaches:** (a) a wrap, beside the lock: the terms of holding that key;
  (b) a grant file, optionally: the terms in force when the grant was made, so a
  subscriber's terms do not move when the lock's do; (c) an item and the manifest (an
  origin default with a per-item override): the terms of public content.
- **Different rights are different locks.** Two wraps on one entry with different terms
  open the same bytes; the difference is legal only, and the RFC says so plainly.
- **Accepting terms is evidence at the home**, like a sign-on token or a payment proof.
  Whether a click-through or a signed document is required is the ladder's, and private.
- **Lines to hold:** it is a citation, never enforcement — nothing on the wire makes
  "delete after 30 days" happen, and §8's refusal stands. No rights vocabulary: the
  reference is opaque, with no machine-readable permissions and no licence codes; an
  agent matches a well-known URL or reads the prose. A reader MUST NOT refuse to show
  public content over terms. A terms reference sends no mention and is never a relation
  (§15.4). The terms document itself should be public.
- **Open for the RFC:** the member's name (`terms`, `rights` and `license` each fit some
  cases badly); whether a `{url}` target may carry a digest; whether the item-level and
  manifest-level use belongs in RFC-6 or is ruled apart as a 0.4 revision.

## 4. How a reader gets content

1. **Discover.** The entry names its locks and their homes. A reader holding any of the
   lock keys unwraps locally: no request, no traffic, nothing logged. This covers nested
   entries whose locks it holds.
2. **Probe.** Holding none, it checks its grant paths at each home (it may have been
   granted the lock, or this one entry, or a lock it holds may have been granted this
   one).
3. **Ask.** Finding nothing, it may send a request, to whichever home it thinks likeliest
   to agree.
4. **Decide.** The home runs its ladder:
   - **pre-approved**: the grant already exists;
   - **automatic**: a rule over origins, rosters (an OPML list is one natural form) or
     presented evidence grants or refuses;
   - **exception**: queued for the lock's owner or their AI delegate, working from the
     owner's standing instructions.
5. **Receive.** A grant file appears, or a refusal, or nothing.

Rules for a delegate, which the RFC should state as client guidance:

- A requester's note is untrusted text and is handled as data.
- A delegate may grant entry keys only, never a lock key.
- An exception does not recurse: a key for an outer entry opens no inner one.

**Where the centralisation lives.** A traditional organisation homes common locks at one
place and every author seals under them (wrapping is symmetric, so any holder of a lock
key can seal under it from their own origin). A decentralised one homes locks per node,
each with its own rosters, which agree only where nodes choose to share one. The wire
says "this lock, ask here" in both cases.

## 5. Widening, and what revocation can mean

**Widening** (declassifying):

| Scope | How | Visible on the wire |
|---|---|---|
| One entry | A new version adding a wrap under the wider lock. Ciphertext unchanged, so it reads as maintenance | Yes: the entry now names two locks |
| One group includes another | A lock-to-lock grant | No |
| One pinned entry | A grant of that entry's key to a lock or origin; the pinned bytes are untouched | No |
| Public | Reveal the entry key in the clear (commit-and-reveal), or publish a new version with the words in place of the cover | Yes |

**Revocation**, stated honestly, in the register of §9:

- It stops future grants and, after a lock is rotated, future content. Nothing else.
- Nothing recalls a key or text a reader already has.
- A pinned version keeps the wraps it was pinned with, forever.
- Widening is one-way.

## 6. Kinds: two companion rulings from the round

These came up while settling blocks and stand apart from Level 3. **Recorded the same
session as decision #100**, in the 0.4 text's thirteenth revision (§5.3, §13.3, §13.7);
reasoning in `v0.4-plan.md` §20. Summarised here because the sealed-content design
depends on both.

1. **An item's kind is fixed at first publication** (withdrawal and its reversal aside).
   A publisher MUST NOT change an item between fragment and thread; a reader that sees it
   happen treats it as it treats a stealth edit (§13.3). Reason: a fragment is a promise
   to whoever quotes it — one layer, one origin's words, bounded size. If it could become
   a thread, a quoter's next republish would pull in nested third-party content it never
   chose, which the quoter's provenance list does not record; under Level 3 that content
   could include sealed entries under other locks. A fragment that needs to grow is
   quoted by a new thread, which is the protocol's own way of composing. Thread to
   fragment is refused by the same rule for simplicity.
   *Evidence:* the studio's editor offers the switch only on drafts; in the session-64
   crawl cache none of the 8 identities held at more than one version changes kind (a
   small sample); and the studio's API refuses the change on a published item
   (`src/api.ts`, `updateItemOperation`: "kind is fixed once an item has been
   published"). So the rule writes down what the reference client already does.
2. **Machine-made items are threads.** An item the client creates on the author's behalf
   (a tangled span, any future automatic split) is a thread, since "fragment" is the
   author's own statement that this is a leaf. **`tangling-plan.md` was revised the same
   session**: parts are threads, and the two refusals that kept them legal fragments (a
   span containing a quote, a span over 1,000 characters) are gone. The reader's `burst`
   rule in `background-plan.md` was widened from "a fragment" to "an item"; it was not yet
   built. Spec §13.7's rule is already kind-neutral ("items … named in its
   `transclusions[]`"); only its closing phrase says "its fragments", a wording fix for
   the same revision.

Also for tangling: a span tangled inside a sealed region inherits the enclosing lock by
default, or tangling would publish sealed text in the clear.

## 7. Identity

The design authenticates **origins**, as Webmention verification does. Which person an
origin belongs to is the approver's own knowledge (a roster, sign-on evidence, an
h-card).

It is meant to sit inside #11 under two conditions, which the RFC must state and Fable
must rule:

- **One key per origin, in the manifest, never inside `author`.** A per-author key would
  make people addressable.
- **Encryption only.** No signing or authorship meaning; that stays with the reserved
  identity work.

The key belongs in the manifest because other clients read it to write grants, and page
markup cannot carry a claim that crosses clients (#41). An h-card may mirror it.

**Shared origins.** Where several people publish from one host, a grant reaches the
origin. Who inside may read it is the house's business, run off the wire as comments are
(tn-7). The house can read everything granted to the origin; a member who cannot accept
that needs their own origin. A person who only reads still needs a minimal origin to hold
a key.

*Not re-read this session:* the identity note's gate (#35) and tn-3 on groups. Opus
checks both against this section while drafting.

## 8. Payments — the direction for RFC-7

*Rewritten session 67 (decision #104). The session-66 text listed five things RFC-6 must
keep true; they hold, and four are now constructs in §3.*

**Principle (Venkat).** Payment rests on competing schemes, as identity does, so the
protocol holds as little opinion as it can and lets any rail and any verification scheme
ride it. Base cases: card payments, x402 and MPP. Older patterns such as NFT gating are
not to be blocked and are not the target. Future bearer tokens may change that.

**Payment supervenes on permission.** It is one more ground on which a home grants a
key, and a paid-up lock is an ordinary lock. On the wire there is one dimension, keys.
R1's finding is why: every rail yields a proof for a verifier and none yields a key, so
the home that holds the key is always the mediator.

### 8.1 Assumptions

The design is built on these. Each is an assumption about demand or about the world, not
a finding, and **RFC-7 must state them in a section of its own** so commenters can
attack them directly. If one is wrong, the consequence named is what to revisit.

1. **Agent-first.** The typical buyer is an agent with delegated spending authority,
   buying fast and often under a standing instruction ("buy anything by this author that
   is about biology and under a dollar"). A person at a checkout page is the minority
   path. *If wrong:* the door's one-exchange shape is over-built and the storefront and
   deep-link paths (§8.4) deserve the design effort.
2. **People set policy, not purchases.** People mostly set spending limits and broad
   preferences; they do not approve individual purchases. *If wrong:* a confirm step
   belongs in clients, still off the wire.
3. **The buyer's side holds the means.** An origin or a reader service keeps a card on
   file, a wallet with a cap, or a scoped payment token, with limits. None of it is on
   the wire. *If wrong:* nothing in the protocol changes; clients do.
4. **Rails compete and will keep changing**, as identity schemes do. x402 and MPP are
   both under two years old and neither is a standard (R1). So the protocol names no
   rail, and any rail must ride unmodified. *If one rail wins outright:* nothing needs
   undoing, which is the point.
5. **Base cases: cards, x402, MPP.** These must work well. NFT and token gating must not
   be blocked and is not designed for. *If bearer tokens on chains become the main
   pattern:* the pass is the hook, and its rules (§9 item 20) are what to revisit.
6. **Every rail yields a proof, never a key** (R1), so a home is always in the path. *If
   a rail appears that releases keys itself* (threshold networks are the nearest): a
   home is a URL and such a network can stand behind one.
7. **Small payments are economic on at least one rail.** Per-entry buying under a dollar
   assumes stablecoin or session-style settlement; cards have a floor near fifty cents
   (R1). *If not:* subscriptions and bundles carry the load, which the lock already is.
8. **Subscriptions are a main relation**, not an afterthought: standing access to a class
   of content for a renewing period.
9. **Readers without an origin are a real population** and will mostly buy at a
   storefront and redeem. RFC-6 already asks implementers whether this population is
   real; RFC-7 depends on the answer.
10. **Descriptions are the seller's own and may be adversarial.** `about`, covers and
    terms are written by the party being paid, and will be read by agents.
11. **Law enforces terms; the protocol cites them.** No mechanism restricts use after
    delivery, and none will.
12. **Per-entry probing is tolerable**: an agent asking a home once per sealed entry, and
    the home seeing what was looked at, is an acceptable cost of keeping prices off the
    wire. *If not:* a static, cacheable offer list at the home is the first remedy; a
    price on the wire is the last.

### 8.2 The door

The request URL of §3.7 answers 402 in the rail's own format. Nothing is added to it.

1. **Hold, then probe, then ask.** A reader that holds a key uses it. One that does not
   checks its grant path. Only then does it ask. An agent never pays for what it holds.
2. **Probe.** A GET with no recipient returns the offer: x402's `PAYMENT-REQUIRED`, MPP's
   `WWW-Authenticate: Payment`, both, or others. The same for everyone; cacheable.
3. **Pay.** The retry carries the rail's credential and names a recipient (origin or
   pass). The answer carries the key and the rail's receipt, and the grant file is
   written.
4. **A person at a browser.** The 402 carries `Link: <…>; rel="payment"` (the registered
   link relation; confirm in the RFC) to a checkout page already bound to the request.
   The person pays; the reader polls the grant path as for any pending request.

**Two doors per entry.** The per-entry URL sells one entry at one version (entry keys are
per version). The per-lock URL sells the class for the current epoch. The agent chooses
by its instruction, from `author`, `about` or the cover, the terms, and the offer.

**No price, currency, rail or "for sale" flag is in any protocol document.** A price
change is a change at the home: no version, no feed event. The cost is that an agent
scanning many sealed items asks the home many times and the home sees what it looked at.
Guidance for the RFC: offers cacheable; a home may serve a static price list in its
rail's format; neither is specified.

### 8.3 Subscriptions

A subscription is standing access to a lock (§3.8). Renewal has no construct: it is
obtaining the next epoch's key. A home that charges automatically writes the grant ahead
of time and the client finds it by probing; otherwise the agent meets a 402 at the lock's
door and pays. A lapsed subscriber keeps the epochs they paid for.

### 8.4 Buying without an origin: vouchers and the pass

People without a blyg will mostly pay at a storefront and redeem. The voucher is opaque
evidence in an ordinary request and needs no wire text. Redeeming it once binds the
seller's subscription record to a **pass** in the person's reader; each epoch's grant
then lands at that pass. How the proof reaches the reader, in order of preference:

1. **Reader-initiated**: §8.2 step 4. No code travels and no convention is needed.
2. **A deep link** from the storefront's success page that the reader is registered to
   open: a `redeem` verb on the handler RFC-4 is designing for "stub this" (#82).
3. **Paste**, the universal fallback.

### 8.5 How the cases ride

| Case | How |
|---|---|
| Card, a person | Reader-initiated checkout link, or storefront plus voucher |
| Card, an agent | MPP with a scoped payment token at the door |
| x402 | At the door, unmodified |
| MPP | At the door, unmodified |
| NFT or token gating | A wallet signature as evidence; the home checks ownership and grants to the current holder's pass or origin. A new holder is granted future epochs; the old one keeps what it had |
| Static-only publisher | A home run by someone else takes payment and writes static grants |
| Threshold networks (Lit) | Not blocked: a home is a URL. R1's durability finding stands — do not seal pinned content to a key a third-party network can retire |

### 8.6 Rules for a buyer's delegate (client guidance)

The mirror of §4's rules for an approver's delegate.

- `about`, the cover and the terms document are untrusted text, handled as data. They are
  the seller's claims and may be written to steer an agent.
- Spending limits are set by a person, per period and per origin, and the delegate cannot
  raise them.
- Whether a delegate may buy a lock (a subscription) or only entries is the owner's rule;
  the RFC proposes entries only by default.
- Keep the evidence: the rail's receipt (what was paid), the entry's commitment and the
  description it binds (what was advertised), the terms reference at its version (what
  was promised).

### 8.7 Disclosed, not ruled

- **Reversal.** A card payment can be charged back for months; a key cannot be recalled.
  The seller's remedy is to grant no further epochs. The protocol says nothing.
- **A third-party home holds the lock key** and can read everything under it. A payment
  service acting as home is a trusted party.
- **Paid content travels with quotes.** A quoter copies the ciphertext and wraps (§3.5),
  so a reader of the quoting thread pays the original home. Nothing was designed for
  this; it follows.
- **On-chain rails create public member lists** off the blyg surface.
- **What a seller learns** differs by rail (R1 §6 item 4).

**Refused in advance, for both RFCs:** any restriction on use after delivery (expiring
rentals, read counts, metering). The design expresses "who gets which key, when" and
nothing else. Batching and sessions inside a rail are the rail's business.

## 9. What the RFC must settle or ask

Each is open. The RFC states the options and a proposal; Fable rules at the edit or at
the close. R4's table (`plans/l3/r4-spec-audit.md`) is the checklist for the first group.

**Wire shape**
1. **A second hash.** An edit to sealed text alone leaves `content_hash` unchanged, so
   Level 2 readers will file it as maintenance (§13.2). Holders need a sealed hash of
   what they read; say what maintenance means for each audience.
2. **Key commitment.** AES-GCM does not bind a key to a ciphertext, so one entry could
   show two readers two texts, and a later reveal would prove nothing. Propose a
   commitment.
3. **Algorithms.** The intersection of browsers, Workers, Go and Python's `cryptography`
   package is AES-GCM, HKDF-SHA-256 and X25519. Python's standard library has no cipher,
   so the stdlib rule (session 29) cannot hold for decryption; say what replaces it.
   Confirm the Workers runtime, which R2 did not cover.
4. **Padding.** Short spans leak their length. Propose bucket sizes.
5. **Locating a span when rendering from `content_md`.** The baked class serves clients
   that render `content_html`; a markdown-rendering client may need a text selector as
   partial quotes have (§10.3).
6. **What stays clear.** Proposed starting point: references (`transclusions[]`,
   `links[]`, `stub_of`) and counters clear, words sealed. Then changelog notes, `author`,
   `media` and its files, `generated[]`, each by R4's rows.
7. **Lock ids are visible**, so strangers can see which entries share a lock. Accept, or
   blind them.

**Surface**
8. **The index and the feed.** Under this design sealed items appear in both with their
   covers, and spans add no events. Confirm against §6.2 and §7, and say what a plain RSS
   reader sees.
9. **Pins.** A sealed version may be pinned; the promise is ciphertext. Say whether the
   protocol says anything about keeping keys.
10. **The carve-out.** The request endpoint is a second dynamic surface (#1, #13), and
    the home URL sits in the entry, not the manifest, to stay clear of #52. Check that
    reading of #52.
11. **Grant path derivation**, and whether hosts that list directories or publish their
    repository defeat it.
12. **Abuse of the request endpoint**: rate limits, and whether every request gets the
    same first answer so the endpoint is not an oracle.

**Behaviour**
13. **Mentions.** Can a sealed item send a verifiable mention (§15.4), given clear
    references?
14. **Generation.** Sealed text fed to a generator comes out in the generating item's
    audience (§5.7). Client policy, as #93 F3 treated quoting across a boundary?
15. **Revocation as a retention event.** Does a conforming reader drop decrypted copies
    when it loses access, as on withdrawal (§13.4)?
16. **Post-quantum.** Grant files wrap keys to classical public keys. Disclose, or
    require a hybrid.
17. **Conformance.** Which clauses change, and whether the live crawler needs to know
    Level 3 before any node emits a sealed entry.

**Added session 67**
18. **`about`**: the cap; the guard against its use as a title; whether a sealed item
    should be required to carry it (the direction says no: `about`, else the cover).
19. **What the commitment binds**: the key and ciphertext (item 2), and the description.
20. **The pass**: grant path derivation from a bare key; what a reader should do about
    copies; whether a pass may be the recipient of a lock key or only of entry keys.
21. **Epochs**: the wrap's shape; whether epoch numbers leak a publisher's billing
    cadence and whether that matters.
22. **Terms**: §3.9's three open points.
23. **`sealed_hash`** (item 1): in the clear or inside the ciphertext.
24. **The request's shape**: how a recipient is named; the per-entry and per-lock URL
    layout, or whether the wrap carries the request URL outright.

**Questions for implementers** (the RFC's own §, as RFC-5 §7): whether readers without
their own origin are a real population; whether one home per organisation or one per node
is what they would run; what evidence their ladder would want; whether inline redaction
as covers is enough or they need more.

## 12. A worked example (session 67; illustrative)

The most complex case: a fully sealed item with a teaser, an `about`, three locks with
their own terms, and the price where it lives. **Field names are illustrative. Three
details are guesses to be settled in the RFC:** the request body's `recipient` shape, the
per-entry URL layout, and whether `sealed_hash` is in the clear.

### 12.1 The item document

```jsonc
{
  "blyg": "0.5",
  "id": "7c9wk2mhq0v3xj8tn5rzfd41bg",
  "kind": "thread",
  "version": 3,
  "origin": "https://blyg.example.org/",
  "author": { "name": "A. Biologist", "url": "https://example.org/" },
  "page": "t/7c9wk2mhq0v3xj8tn5rzfd41bg/",

  // THE COVER. For a fully sealed item this is the whole public face: the feed
  // entry, what RSS and Level 2 readers show, what content_hash covers. A teaser here.
  "content_md": "Gut flora may set the pace of limb regeneration in axolotls. The first results are in, and they are not what we expected.",
  "content_html": "<div class=\"blyg-sealed\" data-blyg-entry=\"e1\"><p>Gut flora may set the pace…</p></div>",
  "content_hash": "sha256:…",

  // Terms for the public cover (an origin default could sit in the manifest)
  "terms": { "url": "https://creativecommons.org/licenses/by-nc/4.0/" },

  "transclusions": [],
  "changelog": [ /* … */ ],

  "sealed": [
    {
      "entry": "e1",
      "about": "Full write-up, 4,200 words: methods, three figures, raw counts for 40 animals, and a failed replication.",

      // Any ONE wrap opens the entry (OR). Each lock has its own terms.
      "wraps": [
        { // subscribers: a class of content, renewing by epoch
          "lock": "k7f3…", "epoch": 12,
          "home": "https://keys.example.org/",
          "terms": { "origin": "https://blyg.example.org/",
                     "id": "1vgtgz0gq5b2c9k7d3m8r4n6xy", "version": 2 },  // pinned: "personal reading"
          "key": "<entry key wrapped under lock k7f3 epoch 12>" },

        { // a different right at a different price: same bytes, different terms
          "lock": "m2qd…", "epoch": 1,
          "home": "https://keys.example.org/",
          "terms": { "origin": "https://blyg.example.org/",
                     "id": "4h8ne0c2w6s9a1x5j3t7bq0mrv", "version": 1 },  // pinned: "republication licence"
          "key": "<entry key wrapped under lock m2qd epoch 1>" },

        { // the lab's own members: no payment, an NDA, a home run by someone else
          "lock": "p9wz…", "epoch": 4,
          "home": "https://access.lab-consortium.example/",
          "terms": { "url": "https://lab-consortium.example/nda-2026.pdf" },
          "key": "<entry key wrapped under lock p9wz epoch 4>" }
      ],

      "commit": "<commitment over entry key, ct, and about (or the cover if about is absent)>",
      "sealed_hash": "sha256:…",
      "nonce": "…",
      "ct": "<ciphertext, padded>"
      // The plaintext is content and may carry its own "sealed" list (AND):
      // e.g. the raw counts under a fourth lock, invisible until e1 is opened.
    }
  ]
}
```

### 12.2 The door

```text
GET  https://keys.example.org/entry/7c9wk2…/v3/e1        single purchase; no recipient = a probe
     (or …/lock/k7f3… for the subscription)

402  Payment Required                                    the same first answer for everyone
     PAYMENT-REQUIRED: <x402 offer: 0.40 USDC on Base …>
     WWW-Authenticate: Payment <MPP challenge: $0.50 card, or 0.40 USDC …>
     Link: <https://pay.example.org/c/abc123>; rel="payment"
     Cache-Control: max-age=3600

POST same URL                                            the agent, inside its spend limit
     PAYMENT-SIGNATURE: <x402 credential>     (or Authorization: Payment <MPP credential>)
     { "recipient": { "pass": "<buyer's public key>" } }      or { "origin": "https://…" }

200  { "key": "<entry key wrapped to the recipient>" }
     PAYMENT-RESPONSE: <the rail's receipt>
```

### 12.3 The grant file

```jsonc
// GET https://keys.example.org/g/<path only the home and the recipient can compute>
{
  "for": { "entry": "7c9wk2…/v3/e1" },       // or { "lock": "k7f3…", "epoch": 12 }
  "key": "<the key wrapped to the pass or to the origin's manifest key>",
  "terms": { "origin": "https://blyg.example.org/",
             "id": "1vgtgz0gq5b2c9k7d3m8r4n6xy", "version": 2 },
  "at": "2026-11-12T17:30:00Z"
}
```

What the example shows: the paywall is two doors (entry and lock); price and rail never
touch the item document; the second lock's terms differ in law and not in bytes; and the
whole `sealed` list is copied as it stands when the item is quoted, so the paywall, the
`about` and the terms travel with the quote.
