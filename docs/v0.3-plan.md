# v0.3 "Trunk" Implementation Plan — threads go cross-client

**Status:** locked design, Fable 5.1, session 22 (2026-09-16). Implementable by
Opus/Sonnet without further protocol decisions; anything below marked ⚠️ FABLE is
deferred, not delegated.

**Sequencing constraint that shaped this plan:** Venkat presents blygger at the
Protocol Symposium on **Thu 2026-09-24, 23:00 UTC** — eight days from the day this
was written. The deck's roadmap slide already names v0.3 as "threads across clients,
Webmention with structural verification". This plan is therefore split into **Phase A**
(the smallest protocol surface that lets a stub cross between the two live nodes and
be verified on the far side — buildable in two or three Opus sessions, live on both
nodes before the talk) and **Phase B** (the rest of v0.3 as the roadmap defines it,
after the talk). Nothing in Phase A is a throwaway: every wire construct it introduces
is the permanent form.

Per decision #21 the normative `protocol-v0.3.md` is drafted **after** Phase A has
been live-tested across the two nodes, not before. §2 of this document is the wire
delta that draft will fold into the 0.2 text.

---

## 1. Objective & non-goals

**Objective.** The social layer over threads, with no AI: an author can quote another
blyg's item into a thread, mark the thread as a response (a *stub*), and the quoted
blyg finds out — reliably, verifiably, without subscribing to the stubber. Stubs stack:
a stub can be stubbed, across clients, and both ends render the stack. This is the
"network of soapboxes" the frozen v0 spec described: no reply primitive, only
public speech that cites.

**Phase A delivers** (demo-critical):
- Cross-client transclusion: `![[id]]` resolves against imported items, baking the
  reader's local snapshot with origin provenance.
- Thread-in-thread nesting, local and remote.
- Stub metadata (`stub_of`) and the one-click stub action, which **absorbs** the
  reading feed's `respond ↗`.
- Webmention: send on publish, receive, **structurally verify**, and surface verified
  inbound stubs in the studio ("detect stubs").
- The `page` field and `rel="alternate"` link that make an item's permalink
  discoverable from its document and vice versa — the latent gap webmention exposed.

**Phase B delivers** (post-talk, still v0.3):
- `forked_from` lineage implementation (shape reserved since 0.1 §5.6).
- Share action (fragment linking a thread, editable summary).
- Own items as hopper members; thread composition from a hopper.
- Stub templates (studio sugar, zero protocol bytes — proposal §3).
- Threads tab ordered by most-recently-updated.
- Optional public "responses" list on a permalink page (§3.4 — Venkat's call).

**Non-goals for v0.3:** anything AI (v0.4's generation hooks are untouched — TK works
as it does today, and TK source references inside scopes are unchanged); any
follow/follower object (decision: "follow is deliberately nothing"); plain-Webmention
acceptance from non-blyg sources as a first-class signal (§2.3.7 — MAY in spec,
dropped by the reference client at 0.3); L3 privacy; multi-tenancy.

## 2. Protocol artifacts (locked — decisions #26–#29)

### 2.1 Cross-client transclusion and nesting (decision #26)

The grammar (0.2 §10.1) is unchanged. What changes is **resolution** and
**provenance**.

**Resolution order** for an own-line `![[id]]` at publish time:

1. A local, currently-published item with that id (fragment **or thread** — nesting
   arrives here; the "fragments only" rule of 0.2 §10.2 is lifted).
2. Otherwise an **imported** item with `remote_id = id` whose local state is
   `current` (or `tombstone` with a pinned-retained snapshot — 0.2 §13.4's retention
   rule is exactly what makes such a snapshot still quotable), and which is **not
   L0** (an L0 row is a wrapper around someone's RSS summary, not their item).
3. Otherwise a publish error, with the existing reasons plus: `source withdrawn by
   origin` (tombstone, nothing retained), `ambiguous id` (see below).

Ids are 26 characters of a 32-symbol alphabet (~130 bits); two different origins
producing the same id is not a real case. The reference client nevertheless treats
**more than one imported match** as a publish error rather than picking one. The
directive names an *identity*, not an origin — that is what lets a thread be moved,
mirrored, or re-hosted without rewriting its source.

**The local snapshot is what gets baked — never a live fetch.** This is the roadmap's
"remote transclusion always operates on the local snapshot" rule, and it is the rule
that makes network cycles harmless: a snapshot is static bytes, so no resolution
recurses. Publish does not depend on the network. Consequence: you can only transclude
what you subscribe to (or have retained via a pin). That is a feature — quoting
follows reading.

**Nesting.** A thread target's `content_html` already contains baked
`blockquote.blyg-transclusion` elements; nesting them is just nesting blockquotes.
Provenance records **direct** transclusions only; deeper layers are inspectable in the
baked HTML's data attributes. The **local DAG check**: a thread MUST NOT transclude a
local thread whose transitive local transclusion closure (walked via stored
`transclusions[]`) contains the publishing thread's own id — this is cheap, and it
stops the only genuinely silly case (a thread quoting a thread that quotes it), which
snapshot semantics would otherwise permit as a finite but useless doubling. Remote
closures are **not** walked: harmless by snapshot, unknowable in general.

**Provenance shape.** `transclusions[]` entries gain an optional `"origin"`:

```json
"transclusions": [
  { "id": "7c9wk2mhq0v3xj8tn5rzfd41bg", "version": 3 },
  { "id": "1vgtgz0gq5b2c9k7d3m8r4n6xy", "version": 1,
    "origin": "https://blyg.protocol-institute.org/" }
]
```

`origin` is **omitted for own-origin sources** (so every 0.2 document remains a valid
0.3 document unchanged) and is the source subscription's *identity origin* per 0.2
§12.2 — the post-redirect fetch origin, never the manifest's self-asserted `site`.

**Baked wrapper.** The blockquote gains `data-blyg-origin` for remote sources only:

```html
<blockquote class="blyg-transclusion"
            data-blyg-id="{id}" data-blyg-version="{n}"
            data-blyg-origin="https://blyg.protocol-institute.org/">…</blockquote>
```

Still no link inside — the provenance link on a page is presentation (0.2 §10.2).
`author` pass-through: the baked HTML is the source's rendered content; a byline
inside the blockquote is presentation, and the reference client renders one for remote
sources ("from *Protocol Institute Blyg* ↗ · snapshot of v1") in the same
injected-provenance line it uses today.

**Republish re-resolves** every directive to the then-current local snapshot, as at
0.2. A source that has since been withdrawn (and not pin-retained) is a publish error
on republish, exactly as a withdrawn local fragment is today — the author removes the
directive or leaves the thread at its current version. Recorded as an open thread
rather than softened: a "freeze this quote at the withdrawn version" affordance would
be the first place withdrawal failed to roll to null, and that is a Fable decision for
another day, made on evidence.

**Snapshot independence** (0.2 §10.4) applies verbatim across origins: later edits,
withdrawal, or pinning at the source never change a baked thread. No auto-pin.

### 2.2 Stub metadata (decision #27)

A **stub** is a thread that declares itself a response to one target. Threads only:
that is the frozen spec's own framing ("stubs are threads, so a stack always looks
like a link to a local thread"), and it is what makes stubs stackable — threads can be
transcluded, so a stub of a stub is nesting, not a new construct.

Thread documents MAY carry a top-level `"stub_of"`, in one of two shapes:

```json
"stub_of": { "origin": "https://blyg.protocol-institute.org/",
             "id": "1vgtgz0gq5b2c9k7d3m8r4n6xy", "version": 1 }
```

for a blyg target (`origin` REQUIRED here even when it is the publisher's own origin —
this object is a citation, and citations are absolute), or

```json
"stub_of": { "url": "https://simonwillison.net/2026/Sep/10/some-post/" }
```

for a plain-web target (an L0 subscription, or anything with a URL). Exactly one
target: a stub responds to one thing. Other transclusions in the body are quotes,
not additional targets.

**The body is the author's.** The protocol does not require the body to transclude
the target — `stub_of` is the machine-readable response marker, and readers rely on
it, never on body inspection. The reference client's stub action *always* starts the
body with `![[id]]` for blyg targets because a stub without the quote is not a stub
in the medium's own aesthetic; an author who deletes the directive has published a
response-by-link, which is legitimate and still verifies (§2.3.5).

**Version agreement rule:** at publish, if the body transcludes the stub target,
`stub_of.version` is set to the version actually baked; otherwise it keeps the value
set when the stub was created (what the author saw). The two can never disagree on a
published document.

`stub_of` lives on **versions** (like `transclusions`), so a pinned version of a stub
carries its own citation, and the live document reflects the latest. A withdrawn
stub's endcap omits `stub_of`, like every other content field — which is also what
makes a withdrawn stub stop verifying (§2.3.6).

Feed: a stub is a thread and appears as one. No feed vocabulary is added; a
reader that wants the marker fetches the item document, which 0.2 §13.1 already
requires for content.

### 2.3 Webmention (decision #28)

Mechanism and verification principle were locked in session 7. This section is the
mechanics.

#### 2.3.1 Advertising an endpoint

- Manifest: optional `"webmention": "webmention"` — a URL, origin-relative allowed,
  resolved against the manifest URL. Present only when the publisher accepts
  mentions. A static export omits the key.
- Permalink pages and the feed page SHOULD carry `<link rel="webmention" href="…">`
  and the endpoint SHOULD also be announced in an HTTP `Link` header on those pages,
  per W3C discovery, so non-blyg senders find it.
- Reference client: `{origin}webmention` (i.e. `{MOUNT}/webmention`) — inside the
  origin surface because it is a protocol surface, unlike `/studio` and `/api`,
  which are host-rooted client internals.

#### 2.3.2 The `page` field and `rel="alternate"` (decision #29)

The reference client has, since 0.2, built remote permalink URLs as
`{origin}f/{id}/` and `{origin}t/{id}/` — a convention 0.2 §4 explicitly calls
presentation, not protocol. Webmention needs a target URL and a way back from a
source page to its item document, so the gap closes now, additively:

- Item documents MAY carry `"page": "t/{id}/"` — the origin-relative URL of the
  item's human-readable permalink. The reference client always emits it. Readers
  SHOULD use it when present and MAY fall back to the `f/`·`t/` convention.
- A permalink page SHOULD carry
  `<link rel="alternate" type="application/json" href="{origin}items/{id}.json">`.
  This is the structural-verification hook: it is how a receiver gets from the
  W3C-standard *source page* to the document it actually checks.

Both are optional for conformance and required of the reference client.

#### 2.3.3 When to send

A publisher SHOULD send a mention for each **remote origin reference** in a newly
published version: every `stub_of` (both shapes), every `transclusions[]` entry with
an `origin`, and (Phase B) `forked_from` when it names another origin. Same-origin
references never generate mentions. A republish re-sends for references that are new
or whose target version changed; unchanged references are not re-sent. Withdrawal of
a stub re-sends the mention once (§2.3.6 — the receiver will find it no longer
verifies and mark it gone), which is the W3C-blessed way to say "deleted".

- **source** = the referencing item's absolute permalink page (`origin` + `page`).
- **target** = for a blyg reference, the target's permalink page (`origin` + the
  target's `page` if known locally, else the `f/`·`t/` convention); for a `{url}`
  reference, that URL.

#### 2.3.4 Endpoint discovery (sender)

1. Blyg target: fetch the target origin's `blyg.json`; use its `webmention` key.
   (The reference client already holds the subscription; one conditional GET.)
2. Otherwise, W3C discovery on the target URL: `Link` header with `rel="webmention"`,
   then the first `<link>`/`<a>` with `rel="webmention"` in the HTML, resolved
   relative to the target. `HEAD` first, `GET` if no header.
3. Nothing found → record `no_endpoint`; do not retry (a static blyg is conformant and
   simply unreachable this way).

**Retry:** an attempt that fails at the network or with 5xx is retried on the cron
tick with backoff **15m → 1h → 4h → 12h → 24h**, then `failed`. 4xx is terminal
(`failed`) except 429, which retries. A `2xx` is `sent`. Delivery is
**fire-and-forget from the author's point of view**: publish never blocks on it, and
the studio shows outbound status as information, not as a publish outcome.

#### 2.3.5 Receiving and structural verification

Endpoint contract (W3C): `POST` with `application/x-www-form-urlencoded` body
`source=…&target=…`.

1. **Syntactic checks → 400:** both absolute `http(s)` URLs; `source ≠ target`;
   `target`'s origin (scheme+host+port) is this blyg's own, and its path names a
   published item — by `page`, or as `items/{id}.json`. Unknown item → 400 (not 404:
   the endpoint exists; the claim is bad). Withdrawn target → accepted (people may
   still respond to a withdrawal).
2. **Rate limit → 429:** more than 60 mentions from one source host in an hour
   (pending or otherwise). Cheap, and enough to keep a queue from filling.
3. **Accept → 202**, upsert the `(source, target)` row as `pending`, and verify
   asynchronously (`waitUntil`). W3C permits synchronous 200/201 too; 202 is the
   honest answer since verification fetches the network.
4. **Verification** (bounded: ≤ 3 redirects, 5 s per fetch, 1 MB body, ≤ 2 fetches):
   - `GET source`. If the response is JSON with a `blyg` key it is the item document.
     If it is HTML, find `<link rel="alternate" type="application/json">` and fetch
     that; it must be a blyg item document. Anything else → **failed**.
   - The document's `origin` must equal the **final source URL's origin** (scheme +
     host + port, trailing slash normalized). A page on one host pointing at a
     document claiming another origin does not verify — this is what stops a mirror
     or an impostor from speaking in a real blyg's name (0.2 §12.2 identity rule,
     applied inbound).
   - The document must not be `kind: "withdrawn"` → else **gone**.
   - **Relation:** `stub_of` naming `{origin: ours, id: target}` → `stub`; else a
     `transclusions[]` entry with `origin: ours, id: target` → `transclusion`; else
     (Phase B) `forked_from` naming a pinned version of the target → `fork`; else
     **failed** — the document exists but does not reference us. "Ours" compares the
     document's asserted origin string against this blyg's own origin, normalized.
   - Success → **verified**, storing the source item's `id`, `origin`, `version`,
     `kind`, relation, the source `author` (pass-through per invariant 6), and the
     source page URL. **No content is stored** — a verified mention is a pointer,
     and what it points at is fetched from the origin when displayed, or not at all.
5. **Re-sent mentions** re-verify and update `last_seen`, `version`, and relation.
   A mention that verified before and fails now becomes **gone** (W3C: the receiver
   SHOULD delete; blygger keeps the row with status `gone`, so a stubber who
   withdraws and then republishes is recognized rather than treated as new).

Verified mentions are **studio signals**. They are never auto-published, never enter
the feed, the archive index, or any item document. They feed the detect-stubs view
(§3.3). Whether an author then *displays* any of them publicly is curation per 0.2
§13.5 (§3.4, Phase B).

#### 2.3.6 Withdrawal interaction

A withdrawn stub re-sends its mention once (§2.3.3); the receiver finds a withdrawn
document and marks the row `gone`. A withdrawn *target* keeps accepting mentions —
its item document is still 200 forever — and the studio shows them under the
withdrawn item. Nothing here cascades: a stub of a withdrawn item is the stubber's
speech and stays published.

#### 2.3.7 Plain Webmention (non-blyg sources)

A receiver MAY accept mentions whose source is not a blyg item, verified the W3C way
(the source document contains the target URL), and MUST hold them **apart** from
structurally verified mentions — a lower class, never in detect-stubs, because link
verification is exactly the trackback-era check that spam defeated. **The reference
client does not accept them at 0.3**: it returns 202 and the row ends `failed` with
reason `not a blyg item`. Revisit on demand.

#### 2.3.8 What a static-only deployment does

Nothing. It advertises no endpoint, receives nothing, and remains fully conformant at
every level. It may still *send* (the static export is produced by a dynamic studio,
which can send at export time); the reference client's export does not, at 0.3.

### 2.4 `forked_from` (Phase B; shape already locked in 0.1 §5.6)

Implementation, not design: a studio "fork" action available on any **pinned**
version (own or imported, since a pinned version is served forever by its origin)
creates a new draft of the same kind with the pinned content as working copy and
`forked_from: {origin, id, version}` on the item — `origin` REQUIRED, matching
`stub_of`'s citation shape and amending 0.1 §5.6's two-field form additively.
Publish-time check: the referenced version must be fetchable as
`{origin}items/{id}/v{n}.json` (one conditional fetch; a local pin needs none).
Sends a mention like any remote reference. ⚠️ FABLE only if implementation finds the
pinned-only rule biting in practice.

## 3. Client semantics (reference client; presentation and workflow, not protocol)

### 3.1 The stub action absorbs `respond` (resolves the session-18 question)

The reading feed's `respond ↗` was a proto-stub built when cross-client transclusion
did not exist. It is **retired as a separate affordance**; the same slot becomes
**`stub ↗`**, and the two overlapping "respond to this" gestures the session-18 note
warned about never come to exist. What survives from `respond`: its discipline of
copying none of the source's *text* for plain-web targets.

`stub ↗` on a reading-feed entry (or a hopper entry):

- **Blyg item** (`l0 = 0`): creates a **thread draft** with working copy
  `![[{remote_id}]]\n\n` and `stub_of = {origin, id, version}` from the imported row,
  then opens the thread editor — live preview already renders the transclusion.
  The author writes; publish bakes the snapshot and sets the version (§2.2).
- **L0 item**: creates a thread draft with working copy `[{title}]({url})\n\n` (the
  old respond prefill, unchanged) and `stub_of = {url}`. No text of theirs is
  copied; the author may quote by hand.

A stub of an **own** item is allowed (`stub_of.origin` = own origin); no mention is
sent. The thread editor shows the stub target above the source pane ("stub of
*Protocol Institute Blyg* → 1vgtgz0g… v1 ↗") and offers "clear stub" which drops the
metadata and leaves the body alone.

**Not coupled to hoppers** — a deliberate deviation from the frozen spec's
"(a) adds to a hopper" step, flagged for Venkat (§7). Rationale: the stub's own
provenance is the record of engagement; a hopper entry created as a side effect is a
second ledger that would drift from the first. Hoppers stay what session 7 made them:
deliberate curation. If a "Stubbed" list turns out to be wanted, it can be *derived*
from `stub_of` rather than stored.

The editorial-cost ruling of session 18 stands: a stub whose body is just the quote
is one click and legitimate; a publish-time nudge is the only lever if it is ever
revisited.

### 3.2 Composer and editor changes

- The `![[` palette (`/studio/fragments/search`) searches **own published items
  (fragments and threads)** and **imported blyg items** (`current`, non-L0), showing
  a source badge for imported ones. Renamed in spirit, not in route.
- Preview (`/studio/preview-thread`) renders imported and thread targets through the
  same walker, so what the author sees is what bakes.
- Publish error banner gains the three new reasons from §2.1.
- The public thread page's provenance line names the origin for remote sources and
  links the remote permalink (`page` if known, else convention).

### 3.3 Detect stubs — `/studio/mentions`

The built-in filter the frozen spec asked for, fed by verified mentions (Phase A) and
later also by subscribed feeds (Phase B: a subscribed origin's stub of a local item,
found by its `stub_of` at import time — the roadmap's original mechanism, now the
second channel rather than the only one).

Lists **verified** inbound mentions newest-first, grouped by target item: source
author/origin, relation badge (`stub` · `transclusion` · `fork`), version, when
first and last seen, a link to the source page, and — the whole point — a
**`stub ↗` button that stubs the stub back**, which requires the stubber to be a
subscription (the local snapshot rule): if it isn't, the button offers "subscribe to
this origin first" via the existing add-by-URL flow. Also shows the outbound queue
(`/studio/mentions` lower half): per published item, each mention's status, for
the author's information only. `gone` rows are shown struck through; `failed` and
`no_endpoint` are informational.

### 3.4 Public display of verified stubs (Phase B, Venkat's call — §7)

0.2 §13.5 already permits displaying curated pointers to others' content with no
protocol surface. A per-item "show responses" toggle that lists verified stubs (title
+ origin + link, **no content**) on the permalink page would be pure presentation and
a much stronger demonstration of "anyone can stub you and you'll know". Not built in
Phase A; if Venkat wants it for the talk it is one afternoon and no wire change.

## 4. Reference implementation

### 4.1 Schema — migration 0007

```sql
-- v0.3 "Trunk". See docs/v0.3-plan.md §4.1.
ALTER TABLE items    ADD COLUMN stub_of TEXT;      -- working copy, JSON (§2.2)
ALTER TABLE versions ADD COLUMN stub_of TEXT;      -- as published, JSON
-- transclusions JSON entries may now carry "origin" (§2.1); no DDL change.
ALTER TABLE imported_items ADD COLUMN page TEXT;   -- §2.3.2, from the item doc

CREATE TABLE mentions_in (
  id TEXT PRIMARY KEY,
  source TEXT NOT NULL, target TEXT NOT NULL,      -- as received, normalized
  target_item_id TEXT NOT NULL,
  status TEXT NOT NULL,                            -- pending|verified|failed|gone
  relation TEXT,                                   -- stub|transclusion|fork
  source_origin TEXT, source_id TEXT, source_kind TEXT, source_version INTEGER,
  source_author_json TEXT, source_page TEXT,
  first_seen TEXT NOT NULL, last_seen TEXT NOT NULL, verified_at TEXT,
  attempts INTEGER NOT NULL DEFAULT 0, error TEXT,
  UNIQUE (source, target)
);
CREATE INDEX mentions_in_target ON mentions_in (target_item_id, status);

CREATE TABLE mentions_out (
  id TEXT PRIMARY KEY,
  item_id TEXT NOT NULL, version INTEGER NOT NULL,
  target TEXT NOT NULL, endpoint TEXT,
  status TEXT NOT NULL,                            -- pending|sent|failed|no_endpoint
  attempts INTEGER NOT NULL DEFAULT 0, next_attempt_at TEXT, last_error TEXT,
  created TEXT NOT NULL,
  UNIQUE (item_id, target)
);
```

`mentions_out` is keyed on `(item_id, target)` so a republish updates the row (new
version, back to `pending`) rather than duplicating it — §2.3.3's "re-send only when
new or changed" falls out of the upsert.

Phase B adds `items.forked_from TEXT` and a nullable `own_item_id` on `hopper_items`
(own items as members; a row has exactly one of `own_item_id` /
`(subscription_id, remote_id)`).

### 4.2 Modules and routes

| Where | Change |
|---|---|
| `transclusion.ts` | `resolveFragment` → `resolveTarget`: local-any-kind, then imported (§2.1 order), ambiguity error, tombstone/pin-retained handling, DAG closure check for local threads. Baked wrapper emits `data-blyg-origin`. `Transclusion` type gains `origin?`. |
| `model.ts` | `publish()` carries `stub_of` from item to version with the version-agreement rule; withdraw clears it on the endcap. |
| `protocol.ts` | `buildItemJson` emits `page`, `stub_of`, `transclusions[].origin`; manifest emits `webmention`. Pinned version JSON carries `stub_of`. |
| `pages.ts` | `<link rel="alternate" type="application/json">` + `<link rel="webmention">` on permalink pages; `Link` header on those responses; provenance line names remote origin; feed page `rel="webmention"`. |
| `importer/store.ts`, `transition.ts` | store `page` from item docs; expose a `findImportedByRemoteId(db, id)` returning all matches. |
| `mentions/` (new) | `discover.ts` (manifest key → W3C discovery), `send.ts` (enqueue on publish, drain with backoff), `receive.ts` (endpoint handler + verification), `store.ts`. |
| `index.ts` | `POST {MOUNT}/webmention`; `scheduled()` also drains `mentions_out`. |
| `studio.ts` | `?stub=subId:remoteId` (replaces `?respond=`), stub header in the thread editor, "clear stub"; `/studio/mentions`; palette search over imported + threads. |
| `importer/studio.ts` | reading feed: `respond ↗` → `stub ↗`. |
| `scripts/export.ts` | omits `webmention` from the exported manifest (the tree is static), keeps `page` and everything else byte-identical. |

### 4.3 Testing the network half

Both sides of webmention are tested in one process against fixture blygs (the
importer tests already serve fixture surfaces through a `FetchLike`): publisher A's
`publish()` enqueues; `send.ts` discovers B's endpoint from B's fixture manifest and
POSTs to B's handler in-process; B verifies by fetching A's fixture page → `rel=
alternate` → item doc; assert the `mentions_in` row. Then the negative table: origin
mismatch (page on host X, document claims origin Y), document without a reference to
the target, withdrawn source → `gone`, HTML source with no alternate link, rate limit,
malformed target. The stub-stack test: A publishes F; B stubs it (S1, remote
transclusion); A imports S1 and stubs it (S2, remote **thread** transclusion, two
levels of blockquote); both documents' `transclusions[]` and `stub_of` are asserted
field-by-field; A's mention to B verifies as `stub`.

### Phase A — before the talk (ordered; commit-sized; each with an acceptance check)

1. **Migration 0007 + types** (§4.1 minus Phase B columns). ✓ migrations apply; suite
   boots.
2. **Cross-client + nested resolution** (`resolveTarget`, provenance `origin`, wrapper
   attribute, DAG closure check, new error reasons). ✓ tests: local thread target
   bakes nested blockquotes; imported target bakes local snapshot with origin;

3. **`stub_of` end to end** (`items` working copy → `versions` at publish with the
   version-agreement rule; item JSON + pinned JSON emit it; endcap omits it).

4. **`page` + `rel="alternate"` + importer stores `page`**. ✓ item JSON carries
   `page`; permalink page carries the link; imported rows populate `page`; export
   byte-identical.
